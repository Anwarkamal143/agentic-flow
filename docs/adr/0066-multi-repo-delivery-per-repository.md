# Multi-repo delivery per Repository: reviews, PR bodies, the ordered Merge Gate and report v7

**Status:** accepted (Phase D, #106; builds the delivery part of ADR-0052). The choices below are routine and reversible. One of them (merging in Delivery Order under `human_approval`) is flagged for human review.

## Context

ADR-0052 decided that each Repository of a multi-repo Job gets its own Integration Review and PR, that every PR body lists its sibling PRs, the Delivery Order and that the PRs are not atomic, that a later Repository's Merge Gate waits until the earlier PR has merged, and that an out-of-order merge done by hand is flagged in the Delivery Report. ADR-0065 stored the Delivery Order with each Repository's `after` list and left the Delivery Report describing only the first Repository.

## Decision

- **Integration Review context.** Each Repository already has its own Integration Task, so its review is already tied to that Repository's `(head, base)`. Its Review Packet now carries `otherRepositories`: every other Repository with Plan Tasks in the same Plan (by name), each with its approved Plan Tasks' diffs `base..head` from its own Factory Clone, cut at 128 KiB each. These are the Plan Tasks' diffs, not the other Integration Branch: integration starts only once every Plan Task is approved, so those diffs always exist, while another Repository's Integration Branch may not be built yet. A Task Result summary is never included, because a reviewer doesn't see what a developer claimed. The field is set on every `integration` packet (empty in a single-repo Job) and never on a `task` packet. `packetVersion` stays 1 because the field is optional. The template text gained one paragraph, so its id is now `integration-review-packet@2`.
- **PR body.** `PullRequestBodyInput.multiRepository` (`null` for a single-repo Job, or a Delivery Order of one Repository) renders a `## Part of a multi-repository Job` section after the opening line. It names the PR count, the not-atomic sentence (`NOT_ATOMIC`, shared with the report), the Delivery Order, and one numbered entry per Repository with its `after` list and its current PR (link and state), "this pull request", or "no pull request opened yet". The `pull_request` Stage opens the PRs in Delivery Order, so a later PR's body names the earlier PR from the start, and the earlier PR's body lists the later one as not opened until the next poll. Nothing new is needed to refresh it: the poller already re-renders every open PR's body on each poll and PATCHes it when the hash differs, so the section updates as siblings open and merge.
- **Merge Gate `delivery_order` condition.** `MergeGateInput.earlier` lists the PRs of the Repositories in this one's `after` list, each with its state and whether its `merge` item is approved. The condition is added only when that list is non-empty, so single-repo gates (and the first Repository's) keep their six conditions unchanged. It sits before `policy` and is `pending` (never `fail`, because a closed PR can be reopened) until each earlier PR has merged. The reason names each PR it waits for, or a Repository with no PR yet.
- **`human_approval`: the merger merges in Delivery Order.** *(flagged for review)* The `merge` Stage runs only once every PR's item is approved. If `delivery_order` waited for an actual merge, web could never be approved before api merged, and api would never merge before web was approved: a deadlock. So under `human_approval`, an earlier PR that is open with its merge approved also passes the condition ("the factory merges it first, in Delivery Order"). `pendingMerges` sorts the Job's PRs by Delivery Order, and the merger already merges them one at a time and stops at the first it can't merge. The order is therefore still enforced where the factory merges. Under `never_auto` only a real merge counts. The alternative was to merge each PR as soon as it is approved, which would change the `merge_approval`/`merge` Stage model that #59 built.
- **Out-of-order merge.** When the poller (or the merger, finding a PR `already_merged`) records a PR as merged while an earlier PR in Delivery Order has not merged, `pull_requests.merged_before_json` (migration 0033) records those PRs' labels, in the same transaction, with a `pull_request.merged_out_of_order` event. The PR record exposes `mergedBefore`. This is judged from what the factory had recorded at that moment: if two merges land between polls, they are seen in polling order (rowid), and the flag may be missed. It is flagged, never prevented (PRODUCT_SPEC "Later": enforcement on GitHub).
- **Delivery Report v7.** It adds `repositories` (every Repository of the Job in the stored Delivery Order, then any others by name), each with its `after` names, a status (`merged`, `awaiting_merge`, `pr_closed`, `delivered_locally`, `not_delivered`), its Integration Branch (state, head, a fetch command once approved) and its current PR label. Each `pullRequests[]` entry also gets `mergedBefore`. A multi-repo Job's notes state the Delivery Order and the not-atomic sentence. Every out-of-order merge is a known limitation. The #105 known limitation ("this report shows the Integration Branch of api only") is gone. `repository` and `integration` still describe the first Repository by name, as in v6, so v6 readers keep working. `job show` prints each Repository when there are several.

## Consequences

- The "Partial Completion: N of M delivered" line and the `blocked` status are #108's and build on `repositories[].status`. The pending contract step is #110's.
- Tests: unit `merge-gate` (+5), unit `pull-request-body` (+3), and the new scenario `multi-repo-delivery` (D1 against the fake GitHub, 3 tests: never_auto in order, an out-of-order human merge, human_approval merging in order). Updated expectations: report v7 in five scenarios, `integration-review-packet@2` in four, and the #105 `multi-repo` scenario's report check.
