# The onboarding wizard: one row, steps written through the ordinary APIs, finish checks from doctor

**Status:** accepted (Phase D, #114; implements ADR-0053). The choices below are routine and reversible. Three are flagged for human review.

## Context

ADR-0053 sets the wizard's steps (basics, harnesses, GitHub, first Project and Repository, policy preset, concurrency, verification), the presets, and what Finish needs: node, git and Claude Code present and a registered Repository, with Claude Code's login a warning where it can't be detected safely. It says each Next writes real configuration through the runtime API, and that the only wizard state is the last step completed, in the database. It doesn't say where that state lives, how a step's writes and its Next relate, what the steps with nothing settable through the API do, or how the login is classified.

## Decision

- **The record.** One `onboarding` row (migration 0037): `last_completed_step` (null before the first) and a `version`, created on the runtime's first start. Nothing else: no drafts, no "finished" flag (finished means the last step is completed). `GET /v1/onboarding` returns the steps, `lastCompleted`, `next` (the first step not completed: where resume opens) and `finished`; `factory status` prints `setup: N of 7 steps completed, resumes at <step>` or `finished`.
- **Next.** `POST /v1/onboarding/complete {step, expectedVersion?}` records one step, in one immediate transaction with an `audit_log` row and an `onboarding.step_completed` event, both as `user:local`. The pure `completeOnboardingStep` allows the first step not completed (it moves on) and any earlier one (going back and pressing Next again keeps the furthest step); a later one is `409 onboarding_step_out_of_order`, so no step is skipped. A stale version is `409 version_conflict`. The Project and Repository step needs a registered Repository (`409 onboarding_step_incomplete`). The verification step (Finish) runs the finish checks and is `409 onboarding_checks_failed`, naming each failing check, while one fails.
- **A step's configuration goes through the ordinary APIs, before its Next.** The dashboard's `/api/setup/<step>` (the second write path beside the Inbox's, same loopback `Host` and `Origin` check, ADR-0022) checks the page's wizard version and the step order first, so a stale page or a skipped step writes nothing, then writes the step's configuration and records Next:
  - **Project and Repository:** "Detect its profile" is a GET form that runs `POST /v1/repositories/inspect` (it writes nothing) and shows the proposal; "Confirm and register" posts the shown profile, creates the Project when no Project has that name (`project_exists` reuses it: the human typed the name here), and registers the Repository (`POST /v1/repositories`). Next is a separate button. No setup command is offered: it is set by a human with `repo profile set` (ADR-0047).
  - **Policy preset:** `POST /v1/factory/config/preset {preset, planApproval?, mergePolicy?}` applies the pure `presetChanges` (ADR-0053's table: Manual and Assisted set `planApproval: required` and `mergePolicy: never_auto` at the Factory Level, Manual also `concurrency.global: 1`; Advanced takes both fields; Controlled autonomy is `400 preset_not_available`). Keys a preset doesn't name are left as they are.
  - **Concurrency:** `POST /v1/factory/config/set-many {changes, expectedVersion?}` sets `concurrency.global`, `perRepository`, `perJob` and `perProjectJobs` (an empty field is left as it is).
  - Both Factory Level writes are one transaction each with one audit row (`factory_config.preset` with the preset's name, or `factory_config.set` with the keys) and one `factory.config_updated` event, all keys or none, under the narrowing check (a Repository wider than the new ceiling refuses the preset with the parent's value named).
- **Basics, harnesses and GitHub show; they don't write.** What they would set (the workspace root, the Harness and its billing, the Token Reference) is in bootstrap `config.json`, which only `factory init` writes and the runtime never does (ADR-0049). The pages show what the runtime and doctor found and say where to change it; their Next records the step only. GitHub's "Skip GitHub: local Delivery only" is the same Next. *(Flagged for review: these three steps write no configuration. Making the runtime write `config.json` would be a new writer of a bootstrap file.)*
- **The finish checks** (pure `onboardingChecks`, `GET /v1/onboarding/checks`) read doctor's report (`onboardingEnvironment`) and the Repository count: node, git, Claude Code (`ok` passes; `missing` or `failed` fails), Claude Code's login, and a registered Repository. The login passes when `claude auth status` exits 0; fails when it exits non-zero (detected as logged out); is a **warning** when the probe gave no exit code (timed out or could not run), which doctor now reports as `detected: false` and the CLI as `unknown`; and passes with API-key billing, which needs no login. *(Flagged for review: ADR-0053 lists only the tools and a Repository as mandatory; a detected logout is treated as a failing mandatory check because every Harness Run would fail.)* GitHub is never a finish check.
- **The dashboard.** `/setup` redirects to the first step not completed (to verification once finished); `/setup/<step>` shows a stepper (steps after the first not completed aren't links), the step's persisted values, and its forms. Finish is rendered disabled while a check fails, and the runtime refuses it anyway. The header gains "Setup". *(Flagged for review: the wizard is offered, never forced: an existing factory sees the "Setup" link and nothing else.)*

## Consequences

- A step's configuration is visible through the CLI (`project list`, `config show`) as soon as its Next returns. If a configuration write succeeds and the Next after it fails, the configuration stays and the refusal page says what changed.
- The Factory Level service gains `setMany` and `applyPreset`; `setKey` is the one-key case of the same transaction.
- Tests: unit `onboarding` (new, 13: the steps, resume, order, every preset, the finish checks); scenario `onboarding` (new, 4, the built dashboard over HTTP: every step with the CLI after each Next and the audited events; resume after a runtime restart, a skipped step and a stale page refused; Finish refused with an unusable Claude Code and the Project step refused with no Repository; a warning for an undetectable login that still finishes).
