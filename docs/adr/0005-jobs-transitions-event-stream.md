# Jobs, versioned transitions and the event stream (Phase A, issue #5)

Choices made while building `factory job create | list | show | cancel`, the transition engine and the SSE stream. The human made one of them (Cancel early); the rest are routine and reversible.

- **Cancel Job comes in now (human decision, 2026-11-08).** #5 needs an API transition that carries a version, and until #6 there is none. So `POST /v1/jobs/:id/cancel` and `factory job cancel` arrive here. They cancel the Stage Runs that are `pending`, `queued`, `blocked` or `waiting_human`. A `running` Stage Run is refused with `409 stage_running`, because stopping a Harness process group is #12's work. Cancelling a terminal Job is `409 job_terminal`.
- **The Job version is the aggregate version.** `jobs.version` is bumped by every change to the Job or any of its Stage Runs, so "the Job I saw" is one number. An operation sends `expectedVersion` in its body. A stale one is `409 version_conflict`, and nothing is written. The CLI reads the Job and sends the version it read. Stage Runs keep their own `version`, which is also checked (`WHERE id AND state = :from AND version = :v`).
- **Transition order (ARCHITECTURE §4.5).** `changeJob` runs in one `BEGIN IMMEDIATE` transaction. It checks and bumps the Job version, then runs the operation's guards, then steps the Stage Runs (each step checks `canTransitionStageRun` and writes `stage_run.<to>`). Last, it re-derives the Job status and stores it, with `job.status_changed` when it changed. It lives in `apps/runtime/src/engine.ts` and moves to `packages/engine` once the Stage handlers (#6) give that package real content.
- **Intake is the creation itself.** `POST /v1/jobs` inserts the Job (status `draft`, version 0) together with its Stage Runs (`intake` already `succeeded`, the rest `pending`), then queues the first pending Stage (`triage`) through the engine, which takes the status to `active`. Events: `job.created`, `stage_run.queued`, `job.status_changed`. All of it is one transaction.
- **Job status derivation** (`deriveJobStatus`, pure, in `packages/domain`). The precedence is: `active` (some Stage Run queued or running) > `blocked` > `waiting_human` (PROGRESS spec issue 9) > `failed` > `cancelled` > `draft` (all pending) > `completed` (every Stage succeeded or was skipped). `rejected` has no Stage Run state that produces it yet; triage rejection (#6) will add one.
- **Workflow Snapshot.** In Phase A there is one hard-coded Recipe, `feature` v1: `intake → triage → discovery → specification → planning → execution → closure`. Its stages are copied into `jobs.workflow_snapshot_json` at creation, and each Stage Run records its `position` in the snapshot.
- **Effective Configuration, Phase A minimal.** The only levels are recipe defaults < Project. The only setting is `maxAttempts` (default 3, range 1–10), which #9 uses. Each value records its source (`recipe` | `project`). `resolveEffectiveConfig` is pure, and its result is frozen into `jobs.config_snapshot_json`. The Project config is replaced through `POST /v1/projects/:id/config` (an explicit operation, strict schema: unknown keys are `400`), with a `project.config_updated` event holding the before and after values. It is the minimum needed to prove that a Job's config is frozen: the full hierarchy stays in Phase D. There is no CLI command for it yet. Re-freezing a Job's config is not built.
- **Outbox publisher.** Events are released by setting `published_at`. This happens on a 250 ms poll, and right after each commit (services call `notify()`). SSE delivers released events only. Each subscriber reads `seq > cursor` from the database and advances its cursor only after a write succeeds. The runtime is the single writer and its transactions are synchronous, so released events are always a prefix of the log. That rules out gaps and duplicates without any in-memory fan-out buffer. Events written during shutdown are released at the next start.
- **SSE contract.** `GET /v1/events/stream[?job=<id>][&after=<seq>]`. Each message has `event: factory`, `id: <seq>`, and `data:` set to the event JSON (the same shape `GET /v1/events` and `GET /v1/jobs/:id/events` return). It resumes after `Last-Event-ID`, else after `?after=`. With neither, it starts at the current end of the log (live only), so a client that wants history lists it first. A malformed `Last-Event-ID` is `400`. A keep-alive comment is sent every 15 s. The response sends `Connection: close`, so shutdown never waits on a reusable stream socket.
- **List APIs.** `GET /v1/events?after=&limit=&job=` and `GET /v1/jobs/:id/events?after=&limit=` page in `seq` order (max 1000 per page). They return committed events, published or not, so they can be one publish tick (≤ 250 ms, usually one `setImmediate`) ahead of SSE. The order and content are the same.
- **IDs:** `job_<16 hex>`, `stg_<16 hex>`.
- **Migration 0002:** `jobs`, `job_repositories`, `stage_runs`. `stage_runs.position` is added beyond ARCHITECTURE §5.
