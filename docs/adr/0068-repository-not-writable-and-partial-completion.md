# `repository_not_writable` and Partial Completion

**Status:** accepted (Phase D, #108; builds the "Not writable (D5)" and "Partial Completion" parts of ADR-0052). The choices below are routine and reversible; two (how the other Repositories are delivered while one is held, and refusing "check again" after that) are flagged for human review.

## Context

ADR-0052 decided that a preflight before each Task's first Attempt checks the Factory Clone and, with GitHub Coordinates, the token's push permission; that a failure blocks the Task with `repository_not_writable` and the exact reason; that the same Blocker replaces `delivery_failed` for a permission lost at push; that dependent Tasks wait and other Repositories continue; and that Partial Completion is not a terminal status, the Job staying `blocked` with the Delivery Report showing each Repository's status, while blocked and after a cancel. Until now, integration started only once every Plan Task of every Repository was approved (ADR-0065), so one stuck Repository held all the others, and the Delivery Report is written only by `closure`.

## Decision

- **The GitHub port reads push permission.** `GitHubPort.getPushPermission(repo)` is `GET /repos/{owner}/{name}`, returning `{push}` from `permissions.push` (absent reads as no push). The fake GitHub serves the endpoint, and `denyPush(name, {apiStillAllows?})` / `allowPush(name)` make it report `push: false` and install a `pre-receive` hook in the bare remote that refuses every push with GitHub's own words ("Permission to owner/name.git denied to …"). `apiStillAllows` refuses only the git push: a permission lost between the preflight and the push.
- **The preflight** runs in the Task scheduler when a claimed Task has no Attempt yet, for Plan Tasks and the Integration Task alike, before any Worktree, Dependency Base or merge: `access(W_OK)` on the Factory Clone and its `.git`, then the port's read. The pure `repositoryWritability` decides: a clone that isn't writable, `push: false`, or a refused read (a 401, 403 or 404: the token can't see the repository) is `not_writable` with the exact reason; a rate limit or a transient failure is `unchecked` (a `task.writability_unchecked` event), and the Task goes on, since the push is the last check anyway. Without a GitHub port (only tests leave it out) GitHub is not asked.
- **The Blocker** is `repository_not_writable`, kind `infrastructure` (so the Stage, and the Job, are `blocked`, not `waiting_human`), its subject the Task itself (no Attempt was made, as `base_merge_conflict` before an Attempt). It opens a Blocker Approval with `retry_check` ("Check again") and `cancel_job`. "Check again" readies the Task and re-queues its Stage, so the preflight runs again; still not writable, it blocks again with a new item.
- **At push.** A git push whose stderr says GitHub refused it for lack of permission (`isPushPermissionRefusal`: "Permission to … denied", "Write access to repository not granted", or an HTTP 403) is no longer `delivery_failed`. The `pull_request` Stage goes on with the other Repositories, then ends `blocked` on `repository_not_writable` (the Integration Task and its approved Attempt as the subject), with a `pull_request.push_not_permitted` event per refused Repository. "Check again" queues `pull_request` again; the PRs already open are recorded and left as they are. The permission read is not repeated at push: git's refusal decides.
- **Partial Completion.** *(flagged for review)* When `execution` would wait on its Blockers, and the only Blockers are `repository_not_writable`, nothing is in progress or failed, and every Plan Task of every other Repository is approved (the pure `partialDelivery`), `execution` succeeds with that reason and `integration` starts with Integration Tasks for the other Repositories only. They go through review, PR and merge as usual. A Task of another Repository that depends on a held one keeps the whole Job waiting: dependents wait. At `closure`, the Delivery Report is written and the Worktrees removed as usual; then, while a Plan Task is still blocked `repository_not_writable`, `closure` ends `blocked` on that Blocker instead of `succeeded`. The Job's status is therefore `blocked`, never `completed`, and the report exists while it is blocked and after a cancel (a cancelled Job keeps its report).
- **"Check again" after a Partial Completion is refused** *(flagged for review)* with `409 partial_delivery_started` once the held Task's Stage is no longer running or waiting: the other Repositories were integrated and delivered without it, and the Stage model has no way to integrate one more Repository into a finished `integration`. Cancelling the Job remains; the operator creates a new Job for the held Repository. The alternative, new `execution` → … → `closure` Stage Runs at `attempt + 1` for the held Repositories (the Replan pattern), is left for a later ticket if wanted.
- **The Delivery Report stays v7** with optional fields (old reports read as before): `outcome` may be `blocked`; each `repositories[]` entry has `blocker` (`{reason, detail}` of its first blocked Plan Task, when it was not delivered); `partialCompletion` is `{delivered, total, line}` from the pure `partialCompletion` (delivered: `merged`, `awaiting_merge`, `delivered_locally`), or `null` when every Repository, or none, was delivered. The statement and a note say "partial completion: N of M delivered", name what was not delivered and why, and that the Job stays blocked until the Blocker is cleared or the Job is cancelled. `job show` prints each Repository's Blocker reason beside its status.

## Consequences

- D5 passes against the fake GitHub: api without push permission is blocked with the exact reason and no Attempt, web is integrated, reviewed, opened and merged, and the report shows "partial completion: 1 of 2 delivered" while the Job is blocked and after it is cancelled.
- The preflight costs one GitHub read per Task's first Attempt.
- A Repository held after a Partial Completion can only be delivered by a new Job.
- Tests: unit `repository-not-writable` (the verdict, the push classifier, `partialDelivery`, `partialCompletion`, the Approval's options and titles); integration `github-port` (+3: the permission read, a refused read, the fake's git refusal); scenario `repository-not-writable` (3: D5 with a cancel; a single-repo Job checked again once the permission is fixed; a refused push raising the same Blocker and pushing once checked again).
