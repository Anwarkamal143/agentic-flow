# The Task Result re-prompt and false claims (Phase A, issue #10)

Choices made while giving an invalid Task Result one re-prompt and proving that the Harness's claims count for nothing. All are routine and reversible.

- **One re-prompt per Attempt, within the Attempt.** ARCHITECTURE §1 says to re-prompt every LLM output once with its validation error, then fail with `invalid_output`. For the developer this is a second Harness Run of the same Attempt (`n` unchanged, the Attempt stays `running`), started only when the first Run exited 0 and left a missing or invalid Task Result. A Run that crashed, timed out or did not start is `harness_failed` straight away: that is Retry (#13), not a re-prompt. A still-invalid result after the re-prompt ends the Attempt `invalid_output`, which routes nowhere (no Rework; ADR-0009), so the Task and the Job fail. Retry is #13.
- **A new Session, not `resume`.** Like the reviewer and proposal re-prompts, the re-prompted Run is `start`, never `resume` (no Harness implements `resume` yet). It works in the same Worktree on the same Task Branch, so the first Run's commits and leftovers are there for it. The Attempt's `session_ref` is the last Run's; both are in the `harness_run.started` events.
- **What the re-prompt carries.** The same Task Packet, rendered by the same template, plus a section listing every violated rule as `[rule] message`. The issues are also stored on that Run's `harness_run.started` event (`reprompt.issues`), and every developer Run's `harness_run.finished` event records its outcome (`valid`, `invalid` with its issues, or `harness_failed`). The template is now `task-packet@3` (its text gains the `{{rejected}}` section, so its hash changes for every prompt).
- **The rules a Task Result can violate.** `result.missing` (no file), `result.regular_file` (a link, a directory or more than 1 MiB; it is not read), `json` (not JSON), and `schema` (TaskResultSchema; the message names the field, such as `status: Invalid option …` or `summary: … received undefined`). These are the same names the proposals and the review use. The exit detail reads `the Task Result was invalid after 1 re-prompt: [rule] message; …`.
- **The rejected result is removed before the re-prompt** (`.factory/` in the Worktree), so the re-prompted Run's result, or its absence, is judged on its own. Only the final Run's Task Result is stored as the Attempt's `task_result` Artifact.
- **Commits are kept.** Nothing in the re-prompt path touches git. After the last Run, the factory inspects the Worktree as before: leftovers become the flagged WIP commit, the head is pinned at `refs/factory/attempts/<id>`, and the Worktree is `preserved`, so an `invalid_output` Attempt's commits stay on the Task Branch in the Factory Clone.
- **Usage** of the Attempt is both developer Runs added together. Token and cost totals are `null` when either Run's is unknown, and the tag is the less trusted of the two (`unknown` > `estimated` > `actual`).
- **Leases** budget for both developer Runs (`attemptLeaseMs` counts the developer wall-clock limit twice).
- **False claims (A3) needed no new code.** Since #7 the factory runs every verification command itself and records criterion Evidence from those runs (`source: commands`), and since #8 approval uses only that Evidence and the review's, never `TaskResult.criteria`. A claim that AC-01 is `met` when the factory's test fails ends the Attempt `gates_failed` with `fail` Evidence for AC-01; the reviewer never runs and the Task is not approved. The claim is kept, unchanged, in the `task_result` Artifact. `tests/scenarios/task-result.test.ts` pins this.
- **The Fake Harness** already gives the n-th developer Run of a Task its n-th response, so a re-prompt takes the next response. Scenarios script it explicitly (the scenario helper fails a test whose script runs out).
