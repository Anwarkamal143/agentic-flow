# Project slots and the fair order (Phase D, #99)

**Status:** accepted (Phase D, #99; implements ADR-0050). The choices below are routine and reversible.

## Context

ADR-0050 gives both schedulers one ordering, `priority_weight + 0.5 × floor(wait_s / 60) − in_flight ÷ project limit` (0 when unlimited), and a per-Project limit `concurrency.perProjectJobs` that counts Jobs with work in flight (a running Attempt or proposal Stage Run), taken as a capacity token in the claim transaction. It doesn't say how a token that belongs to a Job, not to one claim, is held and released, where the limit is read, or how the D2 bound is measured.

## Decision

- **The ordering is one pure function**, `fairOrder` in `@factory/domain` (`scheduling.ts`), over candidates `{projectId, priorityWeight, readyAt}`. Ties go to the longer wait, then to the query's order: time ready by event `seq`, then plan order (ADR-0017) for Tasks; Job creation, then Stage position, for proposal Stage Runs. A Task's weight is `tasks.priority`; a proposal Stage Run's is its Job's priority (always `normal` today, so 0). Time ready is the `ts` of the latest `task.ready`/`task.created` (a Task) or `stage_run.queued` (a Stage Run) event. `in_flight` is the Project slots held now.
- **The aging constants are Factory Level keys,** `scheduling.agingStep` (default 0.5) and `scheduling.agingIntervalSeconds` (default 60), read at each claim.
- **`concurrency.perProjectJobs`** is a Factory Level key and a Project key (a positive integer or `unlimited`; unset is unlimited), not a Job key. It is **read at each claim, never frozen into a Job**: one limit is shared by every Job of the Project, so a per-Job frozen copy would let two Jobs of one Project disagree about it. A Project's own value wins, upward or downward (a capacity value, not a permission value). `resolveProjectJobLimit` returns the value and its source. `config set` and `project config set` say the new value applies from the next claim.
- **A Project slot is a lease row** `('capacity.project', '<project-id>:<i>')` under the lease id `job:<job-id>`, so the primary key makes a slot impossible to hold twice, like ADR-0020's tokens. A claim (`claimNextTask`, `claimNextProposalStage`) of a Job that holds no slot takes the lowest free one in the claim's `BEGIN IMMEDIATE` transaction, or is refused when the Project is at its limit; a claim of a Job that holds one takes none (`projectSlot.kind: held`). A slot is taken under an unlimited limit too, so the Jobs in flight are always counted (and a later lower limit sees them).
- **The slot goes with the Job's last work in flight.** `releaseIdleProjectSlot` deletes it when the Job has no Task lease and no running proposal Stage Run. It runs in `releaseClaim` and at the end of every `changeJob` transaction, so every path that ends an Attempt or moves a proposal Stage Run out of `running` (success, failure, cancel, a Blocker, `waiting_human`) frees it in the same transaction. A Job waiting on a human therefore holds no slot. Between two pieces of its work a Job holds none either, as ADR-0050 says.
- **The proposal-Stage scheduler** keeps its one in-process slot and now claims through `claimNextProposalStage`, which takes the Project slot. A Stage Run a previous runtime left `running` resumes with its Job's slot handed to the new runtime (or a slot taken past the limit when the Job had none: its work is already in flight, so it is counted, never stopped). Recovery's `takeOverClaim` does the same for an Attempt.
- **D2** is measured from the event log: a Job "starts executing" at its first `task.claimed`, and a claim's ready-wait is `task.claimed − task.ready|created` or `stage_run.running − stage_run.queued` (proposal Stages). The scenario creates the Jobs in the worst order for first-come scheduling (a Project's Jobs back to back) with fixed Fake Harness durations (250 ms per proposal Stage, 1 s per developer Attempt).

## Consequences

- A Project's Jobs still interleave their proposal Stages: the proposal scheduler runs one Stage at a time, so between two Stages a Job holds no slot and another Job of its Project may run a Stage. The per-Project limit binds where Jobs overlap, in execution. D2's "each Project has a Job in flight before any Project starts its second" is therefore measured at the first Task claim (PROGRESS spec issue 48).
- The mean ready-wait of a Project with more Jobs includes the time its own Jobs wait on its own limit; with Attempts much longer than proposal Stages that wait dominates and the 2× bound measures the limit, not starvation. The scenario's durations keep the shared queue dominant.
- Work in flight across the upgrade gets its slot when recovery or the proposal scheduler resumes it, past the limit if need be.
