# The path-scope Gate and Rework (Phase A, issue #9)

Choices made while adding the path-scope Gate and turning failed Gates and reviews into Rework instead of failed Jobs. All are routine and reversible.

- **The path-scope Gate** is the pure `checkPathScope` in `@factory/domain`. It reads the diff `base_sha..head_sha` from git as `--name-status --no-renames`, so a rename is judged on both sides: its old path is `deleted` and its new path is `added`. Moving a forbidden file into the writable scope still counts as touching the forbidden path. Every path must match a `writable` glob and no `forbidden` glob. Globs are picomatch globs that match the whole path, case-sensitively, with `dot: true`: a scope glob means paths whether or not they start with a dot, so `test/**` covers `test/.env` and `.github/**` is forbidden as written. There are two rules. `scope.forbidden` lists each path with its kind of change and the glob it matched. `scope.outside_writable` lists each path with its kind. A path that is both writable and forbidden is reported as forbidden only. Paths are sorted and listed once.
- **Where it runs:** after the Task Result checks (missing, invalid, or not `done` keep their own exit reasons) and **before verification**. A violation fails the Attempt `gates_failed`, and no verification command or review runs on out-of-scope work. Changes committed by the factory (the WIP commit) are inside `base..head`, so they are judged too.
- **Gate Findings.** A failed Gate becomes a Finding: severity `high`, blocking, Fault Origin `implementation`, with the Gate's rule (`scope.forbidden`, `scope.outside_writable`, `verification`, `criteria`, `worktree.clean`, `approval`) and, for the path-scope Gate, the offending paths. They are stored on the Attempt (`attempts.gate_findings_json`). The review's Findings stay in `review_findings`. An Attempt's Findings, as the API shows them, are its Gates' and then its reviews'. When a review requested changes, its Findings stand for it: the approval-rule problem "the review requested changes" is not repeated as a Gate Finding.
- **Rework routing** is the pure `routeFailedAttempt`. Only a verdict on the work routes anywhere: `gates_failed` (a failed Gate, also a stale review or Evidence) and `changes_requested`. Every other exit reason (`invalid_output`, `not_done`, `harness_failed`, `review_failed`, `factory_error`) still fails the Task and the Job. Re-prompting an invalid Task Result is #10, Retry and recovery are #13. Among the blocking Findings, the Fault Origin decides, in this precedence:
  1. `spec`: a human Blocker `fault_origin_spec`.
  2. `plan`: a human Blocker `fault_origin_plan`.
  3. `infrastructure`: an infrastructure Blocker `fault_origin_infrastructure`, so the Job is `blocked` (ARCHITECTURE §4.6).
  4. Otherwise, if the Attempt was the last allowed (`n >= tasks.max_attempts`, from the Effective Configuration, default 3): a human Blocker `rework_cap_reached`.
  5. Otherwise: Rework.

  Replanning and re-specification are Phase B, so in this phase the plan and spec routes stop for a human, and the Blocker says so. The Fault Origin of a non-blocking Finding is ignored.
- **Task states.** Rework: `verifying | in_review → changes_requested → ready`, in the transaction that ends the Attempt, so the scheduler claims the Task again on its next pass. The cap: `→ changes_requested → blocked`. A Fault Origin route: `in_review → blocked` (new transition). `changes_requested → blocked` is new as well. A blocked Task stores its Blocker (`tasks.blocker_json`), and `stepTask` sets the Blocker exactly when a Task goes `blocked` and clears it when the Task leaves that state.
- **The Stage Run carries the Blocker.** `execution` settles once no Task is in progress (`ready` … `changes_requested`). It fails if a Task failed. Otherwise, if a Task is blocked, it goes `waiting_human` (when any Blocker is human) or `blocked`, and stores the Blocker (the first human one), with `resume_stage_id` set to itself (ARCHITECTURE §4.3). The Job status is derived from that as before (`waiting_human` / `blocked`). Nothing clears a Blocker yet: the Inbox and answering are Phase B. Cancelling the Job works, and it cancels a `blocked` Task too.
- **A Rework Attempt continues on the Task Branch** in the same Worktree (`preserved → active`), from the same `base_sha`, with a new port block. The earlier commits stay underneath and the new Attempt fixes them on top, because a net revert leaves the path out of `base..head`. A fresh branch per Attempt would throw away work and break the one-branch-per-Task naming. Before the Harness starts, the factory removes `.factory/` from the Worktree, so the previous Attempt's Task Result is never read as this one's. The Attempt records `cause` (`initial` | `rework`, spec issue 6) and `n` (the previous one's plus 1). The Fake Harness already hands the n-th developer Run of a Task its n-th response.
- **Every Attempt stays retrievable.** Its row, its verification runs, Evidence, reviews and Findings are never changed by a later Attempt. Its head is also pinned at `refs/factory/attempts/<attempt-id>` in the Factory Clone, right after the factory inspects the Worktree, so its commits stay reachable even if a later Harness rewrites the branch.
- **Task Packet:** `context.priorFindings` (ARCHITECTURE §7 `prior_findings`) holds the Findings of the Attempt before it, from both its Gates and its review, non-blocking ones included, each with its Attempt id and number. It is empty on an initial Attempt. Only the immediately previous Attempt's Findings are carried: they were raised on the head that the new Attempt builds on. The prompt template is now `task-packet@2`, which adds two rules: the path-scope check is explained, and when `priorFindings` is not empty this is Rework on the same branch, so fix those Findings first. The developer Run is always a new Session (no `resume`).
- **API and CLI.** Attempts gain `cause` and `findings`. Tasks and Stage Runs gain `blocker`. Events: `attempt.started` carries `cause` and the number of prior Findings, `task.ready` carries reason `rework`, and `task.blocked` and the Stage Run event carry the Blocker. `factory job show` prints Gate Findings under each Attempt (`gate  <rule>  <paths>`), `[rework]` on Rework Attempts, the number of Findings carried, and the Task's Blocker.
- **Delivery Report:** the "path-scope Gate is not built" limitation is gone. A Task approved on Attempt n > 1 says so, and says where the earlier heads are kept. For each earlier Attempt that committed out-of-scope paths, it names those paths: the delivered diff no longer touches them, but the commits stay in the branch history. The `worktree.active` event of a reused Worktree carries the Attempt and its new port block.
- **Migration 0006:** `attempts.cause`, `attempts.gate_findings_json`, `tasks.blocker_json`.
- **Human decisions, 2026-11-09.** (1) Only blocking Findings route by Fault Origin: a non-blocking one is advice, never starts Rework or stops the Job, and is reported as open (ARCHITECTURE §4.6 updated; PROGRESS spec issue 20). The `plan`/`spec` human Blocker is the Phase B (B4) extension point for routing back to planning or specification. (2) Findings are raised by failed Gates too (GLOSSARY updated; spec issue 19). A Gate that itself breaks still ends the Attempt `factory_error`, without a Finding, until Retry exists (#13). Tests: a scenario about one Attempt's verdict sets `maxAttempts: 1` and expects `waiting_human` at the cap, with the exact Attempt count; the Fake Harness writes an exhausted script to the runtime's stderr (`FAKE_SCRIPT_EXHAUSTED`), and the scenario helper fails any test whose runtime logged one.
