# The Harness contract, the Fake Harness and the proposal Stages (Phase A, issue #6)

Choices made while making triage, discovery, specification and planning run on their own. All of them are routine and reversible. The first one settles `PROGRESS.md` spec issue 2.

- **No `harness_runs` table (spec issue 2).** Exit tests A1–A7 don't need one. A Harness Run outside an Attempt is recorded as two events, `harness_run.started` and `harness_run.finished` (entity `harness_run`, id = the Harness's execution id). They carry the Stage Run, the Run number `n` (1, or 2 for the re-prompt), the Harness id, the prompt template id and hash, the Session ref when there is one, and on finish the exit, duration, usage (tagged), the outcome (`valid` | `invalid` | `harness_failed`) and any issues. Nothing decides on these events. The Stage Run is the state. Each event is written in its own transaction, because it records an observation and changes no state table. A5's "one `harness.start` per Attempt" concerns Attempts (#7, #11), which have their own table. Revisit this if proposal-Stage usage has to be queried or budgeted (Phase E), or if a proposal Run has to be re-attached after a crash.
- **The Harness comes from runtime configuration only.** `config.json` gains `harness: { id: "fake", script: "/abs/path.yaml" }`. If it is unset there is no Harness, so queued Stages wait (`/v1/status` and `factory status` say so). If the script is unreadable or invalid, the runtime refuses to start and names the problem. The runtime holds an `AgentHarness` and has no other switch, so tests and real runs go through the same code. `claude-code` joins the union with its adapter. `factory init` keeps an existing `harness` entry when it rewrites the config.
- **The contract** (`packages/harness`, ARCHITECTURE §6): `detect()` (installed, version, credentials as presence only), and `start(input)` returning `{ executionId, sessionRef?, events, result, cancel }`. `resume?` is declared and unused. `input.subject` (Job, Stage, Task key) is metadata a Harness may use to name things. It never grants anything.
- **The Fake Harness** runs in-process. Its YAML script lists responses per Stage (`output` is emitted as JSON, `raw` verbatim, plus `exitCode` and `delayMs`). The n-th Run of a Stage for a Job gets the n-th response, so every Job replays the script from the start. A Run past the end exits 1. Unknown keys and Stage ids are rejected when the script loads. Task scripts are #7's work. The Fake becomes a child process if a crash scenario (#11) needs one.
- **A proposal is untrusted.** The output is parsed as JSON, then checked against the Stage's Zod schema, then by code validators. If any of these fail, the Stage gets **one** re-prompt: a fresh Run whose prompt lists every problem (`[rule] message`). A second invalid output fails the Stage Run with `invalid_output`. A non-zero exit, a timeout or a failed start is `harness_failed`, with no re-prompt (an exit code is not an output to correct). The failure (`reason`, `message`, `issues[{rule, message}]`) is stored on the Stage Run (`stage_runs.failure_json`), shown in `job show`, and carried in the `stage_run.failed` event.
- **Rules.** The issue rules are `json` and `schema`. The Specification rules are `spec.mandatory_criterion` and `spec.unique_codes`, and each AC also needs a `verification` (schema). The Plan rules are `plan.unique_task_keys`, `plan.task_repository` (a Repository of this Job, by name or id), `plan.valid_globs` (relative POSIX, no `.`/`..`/empty segment, no backslash or negation, balanced under picomatch `strictBrackets`), `plan.dependencies_exist`, `plan.no_cycles` (the message gives the cycle), `plan.criteria_exist`, `plan.mandatory_criteria_covered` and `plan.unique_verification_keys`. The overlap check for writable paths of Tasks that can run in parallel (ARCHITECTURE §3) waits for parallel execution (Phase B).
- **Artifacts are content-addressed.** The content is canonical JSON (2-space indentation, trailing newline). It is stored at `<home>/artifacts/sha256/<2>/<hex>.json`, mode 0400, and written once (same content, same file). Every read checks the bytes against the recorded `sha256:<hex>`, and `GET /v1/artifacts/:id/content` serves exactly those bytes. Rows are only inserted, and there is no route that changes or deletes one. The Artifact row, the rows taken from it (Acceptance Criteria, Tasks), `stage_run.succeeded` and the next Stage's `queued` all commit in **one transaction**. So a succeeded Stage has its Artifact, and it is never run or generated again, also not after a restart. Kinds: `triage`, `discovery`, `spec`, `plan`.
- **Recovery, minimal.** A proposal Stage Run left `running` by a dead runtime is run again at the next start. Its Run lived in the dead process and nothing was stored for it. Shutdown cancels a Run in flight and leaves its Stage Run `running` for that reason. Known gap: a crash between the first invalid Run and the re-prompt gives the Stage a fresh pair of Runs.
- **Tasks.** `tasks.definition_json` holds the validated Plan entry (objective, role, risk, scope, dependencies, covered ACs, verification). It replaces ARCHITECTURE §5's `packet_json` for now, because a Task Packet needs the Worktree and `base_sha`, which only exist at dispatch (#7). A Task with no dependencies starts `ready`, otherwise `pending`. `max_attempts` comes from the frozen Effective Configuration. After planning, `execution` is `queued`, waiting for the Task scheduler (#7). Cancelling a Job also cancels its `pending` and `ready` Tasks (`task.cancelled`).
- **One prompt template**, `proposal-stage@1`, for all four Stages. It holds the Role, what the Stage asks for, the Job, its Repositories, the earlier Artifacts, any rejected issues, and the output JSON Schema (`z.toJSONSchema`). Its hash is recorded on each `harness_run.started`. The working directory is the Factory Clone.
- **Stage handlers stay in `apps/runtime`** (`scheduler.ts`, `proposals.ts`). This revises ADR-0005's plan to move the engine into `packages/engine` at this point: nothing else consumes it yet, and the handlers need the runtime's DB, Artifact store and Harness. Move it when a second consumer exists.
- **Not built:** triage rejection (spec issue 13 stays open), Harness progress storage (events are drained and counted), and a CLI for setting the Harness (edit `config.json`).
- **IDs:** `art_`, `ac_` and `tsk_` plus 16 hex digits. **Migration 0003:** `artifacts`, `acceptance_criteria`, `tasks`, `task_dependencies`, and `stage_runs.failure_json`.
