# Task execution, factory verification and local delivery (Phase A, issue #7)

Choices made while making a ready Task run in a Worktree, get verified by the factory, and be delivered as a local branch. All are routine and reversible.

- **A separate Task scheduler, one slot** (`apps/runtime/src/execution.ts`). It runs the `execution` and `closure` Stages. The proposal `StageScheduler` keeps its own slot, so a long developer Run doesn't hold up another Job's triage. "Single concurrency slot" (ROADMAP Phase A) applies to Task execution. A Job's `execution` Stage Run stays `queued` until its first Task is claimed, so a Job whose Task waits for the busy slot can still be cancelled.
- **Claim:** one versioned Job transaction inserts the `('task', id)` lease (`ON CONFLICT DO NOTHING`; zero rows aborts) and moves the Task `ready → claimed`. Task transitions go through `stepTask` (state + version guarded, `task.<to>` event) inside `changeJob`, so they bump the aggregate Job version like Stage Runs do (ADR-0005). There is no heartbeat yet (#13): `expires_at` covers the Run plus verification, and nothing reads it.
- **Worktree:** `<workspace_root>/<repo-id>/<job-id>/<task-key>` on `factory/<job-id>/<task-id>-<task-key>`, made with `git worktree add` in the Factory Clone only, from `origin/<default>` after a `git fetch origin` (falling back to the local default branch). States `active` (created) → `preserved` (Attempt over) → `removed` (in `closure`, after the Delivery Report is recorded). Removal is `git worktree remove` without `--force`: if git refuses, the Worktree stays `preserved` and a `worktree.remove_failed` event says why. The branch always stays.
- **Ports:** each Worktree leases the lowest free block of 10 from 42000 (`('port_block', '<base>')` lease, released at removal). `worktrees.port_base` keeps the number after release. The Run and the verification commands get `FACTORY_PORT_BASE` and `PORT`.
- **Tier 0 guardrail** (`packages/harness/src/guardrail.ts`), for the Harness process and every verification command: the environment is built only from an allowlist (`PATH HOME LANG LC_ALL LC_CTYPE TERM TMPDIR USER LOGNAME SHELL TZ`) plus the factory's own variables (`FACTORY_JOB_ID FACTORY_TASK_ID FACTORY_ATTEMPT_ID FACTORY_PORT_BASE PORT CI=true`). stdin is `/dev/null`, the working directory is the Worktree, and the process runs in its own group, which gets SIGTERM and then SIGKILL at the wall-clock limit. It is a guardrail, not a sandbox, and the Delivery Report says so. `HarnessStartInput.env` is the complete environment, and a Harness never adds the runtime's own to it. Proposal Runs get the same allowlist.
- **The Fake Harness runs Tasks as a child process** (`fake-worker.js`) under that guardrail. Its script gains `tasks: { <task-key>: [response…] }`, where each response has `steps` (`write`, `delete`, `commit`, `run`) plus `result` (JSON) or `resultRaw`, and `exitCode` and `delayMs`. The n-th Run of a Task in a Job gets the n-th response. ADR-0006's "child process when needed" is now true for developer Runs.
- **Task Packet `packetVersion: 1`**, rendered by template `task-packet@1`. The packet is stored on the Attempt (`attempts.packet_json`, settling spec issue 14). The template id and hash, the Harness id and its detected version are columns of the Attempt. `mayAskQuestions: false` until Phase B.
- **After the Run, the factory trusts nothing:**
  1. Leftovers (tracked or untracked, not ignored) are committed by the factory as `wip: …`, with `Factory-WIP: true` trailers, `--no-verify` and no signing. The SHA is `attempts.wip_commit`, and the Delivery Report flags it. Nothing is discarded.
  2. `head_sha` and the commits `base..head` come from git. A commit the Task Result lists that isn't on the Task Branch is a protocol violation (`result.commits_exist`), recorded on the Attempt and in the report.
  3. The Task Result is read from `.factory/result.json`, which `/.factory/` in the Factory Clone's `info/exclude` keeps out of every commit. It is stored as a `task_result` Artifact (the claim, as data).
  4. Every verification command runs in the Worktree. Its exit code becomes a `verification_runs` row and a `verification` Evidence row, its output becomes a `log` Artifact, and both are tied to `(head_sha, base_sha)`. If HEAD moves during verification, the Gates fail as stale.
- **Criterion Evidence before review exists:** a Plan's verification command may name the criteria it verifies (`criteria: [AC-01]`; new rule `plan.verification_criteria`). Each criterion the Task covers gets a `criterion` Evidence row: `pass` if all its commands passed, `fail` if one failed, `not_tested` if none names it. **Approval rule until #8:** every required command exits 0, HEAD is unchanged, and every mandatory covered criterion is `pass`.
- **Stopgaps until their tickets land** (each is an honest terminal state, never a silent wait):
  - A failed Gate, an invalid or missing Task Result, a Task Result status other than `done`, a Harness that did not exit 0, or a factory error **fails the Attempt and the Task** (`exit_reason` `gates_failed` | `invalid_output` | `not_done` | `harness_failed` | `factory_error`).
  - `execution` then fails with the new Stage failure reason `task_failed`, and the Job is `failed`. Rework is #9, the re-prompt for invalid output is #10, and questions are Phase B.
  - Shutdown cancels the Run in flight and leaves its Attempt `running`. Recovery is #13.
- **Usage** is recorded per Attempt as `{tag, inputTokens, outputTokens, costUsd, durationMs}`. The Fake reports `unknown`.
- **Closure** writes the Delivery Report (`report` Artifact, `reportVersion: 1`). It contains, per approved Task: the branch, base and head, commits with subjects, changed files, the WIP commit, verification exit codes, the criterion verdicts, and `fetchCommand` = `git fetch '<clone>' '<branch>:<branch>'`, which run from the source checkout creates the branch there. It also lists the computed known limitations. Then come Worktree removal and `closure: succeeded`, and only then is the Job `completed`.
- **API:** `GET /v1/jobs/:id/attempts` (with verification runs and Evidence) and `GET /v1/jobs/:id/worktrees`. Artifacts gain `taskId` and `attemptId`, and the kinds `task_result`, `log` and `report`. `factory job show` lists the Attempts, their Evidence and the delivery.
- **IDs:** `wt_`, `att_`, `lse_`, `vr_` and `evd_`. **Migration 0004:** `attempts`, `leases`, `worktrees`, `verification_runs`, `evidence`, plus `artifacts.task_id` and `artifacts.attempt_id`.
- **Review hardening.**
  - **The result file is untrusted.** It is read only if it is a regular file of at most 1 MiB, never through a symbolic link (rule `result.regular_file`). A branch that commits the reserved `.factory/` path is a protocol violation (`result.not_committed`).
  - **Planted git config can't run code with the runtime's secrets.** Every factory git call in the Factory Clone or a Worktree runs with `core.hooksPath=/dev/null` and `core.fsmonitor=false`. Except `fetch`, they also run with a minimal environment (`PATH`, no user or system git config), so a configured driver that does run sees no secrets. `fetch` keeps the runtime's environment for SSH agents and credential helpers.
  - **Verification must leave the Worktree as it found it.** Modified or untracked files after verification fail the Gates, because the Evidence would no longer match `head_sha`.
  - **No untracked Worktree.** The packet is built before the Worktree is created.
  - **Usage always has a tag**, `unknown` when the Harness did not start.
- **Known gaps.**
  - Port blocks of failed Jobs' Worktrees stay leased: they are released only at removal, and only closure removes.
  - Closure records the report and completes the Stage in separate transactions; a crash between them is recovery's concern (#13).
