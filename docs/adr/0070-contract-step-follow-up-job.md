# The contract step as a follow-up Job

**Status:** accepted (Phase D, #110; builds the "contract step" part of ADR-0052, and spec #93 story 60). The choices below are routine and reversible; two (the `plan.contract_criteria` rule, and offering the follow-up only when every Repository's PR merged on GitHub) are flagged for human review.

## Context

ADR-0052 decided that the contract step (removing the old interface) is never part of the Job: the planner marks contract Tasks deferred, they don't run, and once every PR merged in Delivery Order an Approval offers "Start the contract Job for api?" with the deferred Tasks as its description; the Delivery Report lists the step as pending. It also decided that the planner writes the contract (the expand-step interface) into the upstream Task's Acceptance Criteria. Until now a Plan Task had no way to be deferred, and the planner was told nothing about contracts.

## Decision

- **Plan schema.** `PlanTaskProposal.deferred` (boolean, default `false`, so every stored Plan reads as before). A deferred Task is validated like any Task (Repository, scope, profile commands, criteria that exist), but only the Tasks that run make the Delivery Order, the overlap check and mandatory coverage. The contract step depends on the consumers' migration in the other Repository, so counting its edge would make every expand → migrate → contract Plan a cross-repo cycle. New rules: `plan.deferred_dependency` (a Task that runs may not depend on a deferred one: it would never be ready), `plan.no_runnable_task` (at least one Task runs), and a mandatory criterion covered only by a deferred Task is reported as uncovered ("deferred Tasks do not").
- **Never dispatched.** `persistPlanTasks` writes no Task row for a deferred entry: it can't be claimed, integrated or cancelled, and a Replan that defers a kept Task cancels it like any Task the new Plan drops. The deferred entries stay in the stored Plan; `GET /v1/jobs/:id/plan` lists them as `deferredTasks` (not in `tasks`, the waves or the estimate), and `plan show` and the dashboard Plan view show them apart.
- **The contract in the upstream Task's criteria (story 60).** *(flagged for review)* Acceptance Criteria come from the Specification, so the planner can't add one; what it can do is make the upstream Task cover the criteria that state the interface. `plan.contract_criteria` refuses a Plan in which a Task that another Repository's Task depends on covers no Acceptance Criterion. The planner prompt (`proposal-stage@8`, its hash now covering the new text) tells a planner of a Job with more than one Repository to write the interface into the upstream Task's objective, list the criteria that verify it in its acceptance, change interfaces expand → migrate → contract, and mark the contract step `"deferred": true`. A single-repo planner is told nothing about contracts.
- **The Delivery Report** stays v7 with an optional `contractStep` (`null` before #110 and when nothing was deferred): `status: pending`, the Repositories and the deferred Tasks (key, title, Repository, objective, dependencies, criteria codes) and a line. A note says whether the follow-up is offered (every PR merged), or why not: a local delivery is never seen merged, and a Job whose PRs did not all merge (a failure, a Partial Completion) offers none; in both cases the operator creates the Job by hand. `job show` prints a "Contract step (pending)" section. The report is written once and never regenerated, so it stays "pending" after the follow-up Job is created; the Approval's decision records that Job.
- **The Approval.** *(flagged for review)* A new kind, `contract_job`, opened by `closure` in the transaction where it succeeds, when the report lists a contract step and every Repository's status is `merged` (pure `contractJobOffered`); at most one per Job, so a resumed closure never opens two. It holds no Stage (the Job is already `completed`), its subject and evidence are the report Artifact, and its options are `start_job` (recommended) and `decline`. Its question is "Start the contract Job for api?" and its reason lists the deferred Tasks. A `closure` that ends blocked (Partial Completion) opens none.
- **The follow-up Job.** `start_job` creates the Job in the decision's transaction (`JobService.createIn`): the same Project, the contract step's Repositories (by name in that Project), the title `Contract step: <title>` (cut to 200) and the deferred Tasks as its description, each with its objective, the Tasks it came after in the original Job and its criteria with their text from the original Specification (pure `contractJobRequest`, cut to 20 000). The Job is created by the deciding human (`createdBy`, the `job.created` actor) with `followUpOf` in the event; the decision stores `followUpJobId`, which `inbox show` prints. It is an ordinary Job from there: triaged, specified, planned and approved under the Project's configuration at its creation, with nothing carried over (its description is the only link). `decline` creates nothing.

## Consequences

- A multi-repo Job can carry an expand → migrate → contract Plan; the contract step can't be forgotten (report, Inbox) and can't run before every PR merged.
- The follow-up Job's description is the original planner's output, shown to the follow-up's agents as the Job description (as any operator-written description); it grants nothing.
- Tests: unit `plan-validation` (+6: the default, the Delivery Order and overlap without deferred Tasks, the dependency rule, mandatory coverage, no runnable Task, `plan.contract_criteria`), unit `contract-step` (new, 6), scenario `contract-follow-up` (new, 3: the deferred Task never a Task of the Job and listed by the plan view and `plan show`, no item while a PR is unmerged, the report's pending step and note and `job show`, the item once both merged, `start_job` creating the follow-up over api that waits at plan approval, a second decision refused; the multi-repo planner prompt with the contract rules and `proposal-stage@8`; a single-repo prompt without them); `verification-commands` expects `proposal-stage@8`.
