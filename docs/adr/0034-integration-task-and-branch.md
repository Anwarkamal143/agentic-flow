# The Integration Task and the Integration Branch (local integration)

**Status:** accepted (#55, Phase C). Routine and reversible choices inside ARCHITECTURE §14, the Phase C grilling (Q2, Q3, Q10, Q24, Q25) and the GLOSSARY.

## The `feature` Recipe, version 3

- Version 3 adds the `integration` Stage between `execution` and `closure`. `featureRecipe(version)` (`@factory/domain`) keeps version 2 as it was; a Job freezes its Workflow Snapshot at creation, so a Job created at version 2 has no `integration` Stage Run, gets no Integration Task, and its closure follows `execution` as before. Its Delivery Report has `integration: null` and offers the leaf Task Branches as in v3 of the report.
- A test-only `FACTORY_TEST_RECIPE_VERSION=2` (like `FACTORY_TEST_CRASH_AT`) makes new Jobs freeze version 2, so a scenario proves such a Job runs unchanged. An unknown value stops the runtime at boot.

## The Integration Task

- **Who makes it.** The factory, never the planner. In the transaction where `execution` succeeds (`settleExecution`), the pending `integration` Stage Run is queued and one Task of kind `integration` is created, `ready`, for each Repository the newest Plan has Tasks in. A failed `execution` skips `integration` (reason recorded) and queues closure for the partial results.
- **`tasks.kind`** (`plan` | `integration`, migration 0016, default `plan`). Its key is `integration`. `plan_artifact_id` is the Plan whose Tasks it integrates. The unique key index is partial (`kind = 'plan'`) so a planner Task keyed `integration` can't collide; a second partial index keeps one Integration Task per (Plan, Repository).
- **Its definition** (`integrationDefinition`, pure): writable paths are the union of that Repository's Plan Tasks' writable globs (Q24). Forbidden globs are **not** carried: one Task's forbidden path may be another's to write, so their union could fail the combination of two compliant Tasks. Covered criteria are the union. Verification is every command the Plan Tasks list, a command shared by several run once (required if any required it; verifying every criterion any of them named), keys kept unique (`test`, `test-2`, …). The highest risk. It depends on nothing in the Plan. Caps come from the Effective Configuration.
- **Never part of the Plan.** The carry-over (`persistPlanTasks`) reads Plan Tasks only and cancels every unfinished Integration Task (`cancelReason: replan`, Worktree preserved). A new Integration Task rebuilds the branch once the new Plan's Tasks are approved (Q25). Plan Edit, the plan view's Tasks, waves and estimate, `settleExecution` and `settleIfNothingToClaim` see Plan Tasks only. The plan view lists `integrationTasks` apart. `job show` and the dashboard mark it "Integration Task, factory-created, not in the Plan".
- **Its Stage.** A Task runs in `stageOfTask(kind)`: `execution` for Plan Tasks, `integration` for the Integration Task. The claim joins on it and moves that Stage `queued → running`. Blocker and Question items hold it, a cleared Blocker re-queues it, and a cancel is detected on it (`task-stage.ts`). `settleIntegration` ends `integration` by the keep-going rule `execution` uses (`executionOutcome`), and runs at the end of every `settleExecution`, so every existing settle point covers it.

## The merge Attempt

- **Cause `merge`.** The Integration Task's first Attempt runs no Harness (`harness_id: factory`, template `none`). It counts toward `maxAttempts` like an initial Attempt. A merge Attempt interrupted before its Gates is merged again, never handed to a Harness. A later Attempt (a Rework after a failed Gate, after a grant) is an ordinary developer Attempt on the Integration Branch, in the same Worktree.
- **Under the clone's setup lock** (ADR-0020): `git fetch` (so the base is the default branch as it is upstream now, `refs/remotes/origin/<default>`), then the approved Task Branches merged onto it in `integrationOrder`: topological, ties broken by Task key (the smallest ready key at each step, not Plan order). Each merge is `git merge-tree --write-tree`, then `git commit-tree` with two parents (the result so far, the Task's approved head), even where a fast-forward was possible: `--no-ff`. Subject `Merge <task branch> (Task <key>) into factory/<job-id>/integration`, trailer `Factory-Integration: <key>`. Only objects are written until the result is known.
- **Then the branch.** `factory/<job-id>/integration` is created at the result in a new Worktree named by the Task id (`<job>/<task-id>-integration`). In a rebuild after a Replan the branch exists, checked out in the cancelled Integration Task's preserved Worktree. `releaseBranch` detaches that Worktree at the same commit (its files and commits stay; every Attempt head stays at `refs/factory/attempts/<id>`), then `worktree add -B` moves the branch. Nothing was published (no pull request is opened yet), so no Approval is needed (Q25); once a PR exists, the `integration_rewrite` Blocker will gate this.
- **Verification** (`verifyMerge`): the path-scope Gate over `base..head` against the union scope, every de-duplicated command, `worktree.clean` and the mandatory-criteria check. Every Verification Run and its Evidence records the integration `(head_sha, base_sha)`. Pass → Attempt `passed`, Task `approved`. No review runs here: the Integration Review is its own Stage (#56). A failed Gate ends the Attempt `gates_failed` with Gate Findings and is routed by `routeFailedAttempt` like any failed Gate: Rework under the cap, else the `rework_cap_reached` Blocker Approval (grant, replan, cancel).

## Conflicts: the human route

A conflicting merge makes no Attempt and no Worktree. The Task is blocked with `base_merge_conflict` (subject: the Task itself), naming the conflicting Task Branch, its head, the base, the branches already merged and the paths. Its Blocker Approval offers replan and cancel the Job. Its text (title "Integration Task can't build the Integration Branch: a Task Branch conflicts", and the detail) is what `replanFeedback` sends the planner, so the conflict becomes the replan feedback. A Replan may now replace an active `integration` (`activeTaskStage`): it supersedes it and adds new `planning`, `plan_approval`, `execution` and `integration` Stage Runs. The automatic integration agent is `IntegrationConflictRoute`, an interface only (ARCHITECTURE §14).

The Plan validator keeps unordered Tasks' writable paths disjoint (ADR-0017), so two Task Branches conflict only through what their bases carry (for example a Task started on a default branch that was later reset, or git's directory-rename detection). The scenario builds the first case.

## The Delivery Report, version 4

v3 (ADR-0028) plus `integration`: the branch, its state, base and head, the Task Branches merged in order, the verification on the head, and why it did not finish. Once its verification passed, it is what is offered (one `fetchCommand`); the Task Branches stay listed but are not offered separately. With no Integration Task (`feature` v2, or a failed execution), `integration` is `null` and the leaves are offered as before. A failed `integration` makes the outcome `failed`. The Phase C grilling (Q21) called the report with the PR link "v4"; that one will be v5.
