# Config export and import: the document, the configuration version and one audited apply

**Status:** accepted (Phase D, #113; implements the import part of ADR-0049). The choices below are routine and reversible. Two are flagged for human review.

## Context

ADR-0049 asks for `factory config export` (YAML of the Factory Level, Projects and Repositories keyed by name, Token References only) and `factory config import <file>` (validated, diffed, applied with `--apply --expect-version` as one transaction with one `config.imported` event and one audit row holding the diff; it may create Projects, refuses unregistered Repositories and a lower level wider than its parent). It does not say what a Repository's entry holds, which version `--expect-version` names, or what a level left out of the file means.

## Decision

- **The document** (`ConfigDocumentSchema`, `packages/domain/src/config-import.ts`): `format: factory-config@1`, `factory` (the `FactoryLevelConfigSchema`), and `projects` keyed by name, each with `config` (the `ProjectConfigSchema`) and `repositories` keyed by name. A Repository entry is `mergePolicy`, `mergeMethod`, `intakeLabel` (null: none) and `profile` with the settable profile fields (`packageManager`, `commands`, `instructionFiles`, `sensitivePaths`, optional `requiredChecks` and `setup`). Every schema is strict and the levels' own, so an import is validated exactly as `config set` is. Registration facts (source, Factory Clone, GitHub Coordinates) and what only detection writes (detection status, CI files, the confirmation stamp) are not exported and cannot be imported.
- **No token value can be in it.** No level stores a token: the Token Reference is in `config.json`, which is bootstrap-only (ADR-0049) and is not exported. Text a human typed (a setup or profile command) was redacted when it was stored, so it is exported redacted.
- **What a file names it gives in full; what it leaves out is kept.** `factory` is required and replaces the Factory Level (a key left out is unset). A named Project's `config` replaces the Project's, and a named Repository's entry replaces its fields. A Project or Repository the file leaves out is unchanged: an import never deletes (Project deletion is out of scope, Q34).
- **The diff is pure** (`configImportDiff(current, incoming)`): the export of what is stored against the file, leaf by dotted key (`profile.commands.test.run`; lists compare whole, key order never counts), ordered Factory Level, then Projects by name with their Repositories by name; a new Project is a `create_project` entry before its keys. It refuses a Repository not registered in the named Project (`repository_not_registered`, naming where it is registered and `factory repo add`), and runs `configTreeViolation` (ADR-0057) over the whole resulting tree, Projects left out included (`config_widens_parent`). A permission value made wider at its own level is allowed and flagged `widens` (an unset `planApproval` reads as the recipe's `required`; an unset Factory or Project `mergePolicy` is no ceiling, wider than any value).
- **The configuration version.** `--expect-version` names a new counter, `factory_level.config_version` (migration 0036), bumped in the transaction of every configuration change: `config set`, `project create`, `project config set`, the whole-config Project route, `repo add`, `repo profile detect|set`, `repo intake set|off`, and an applied import (once). *(Flagged for review: the Factory Level's own `version` counts only Factory Level changes, so it would miss a Project changed between the diff and the apply.)* A new configuration writer must call `bumpConfigVersion`.
- **API.** `GET /v1/config/export` → `{configVersion, document}`. `POST /v1/config/import {document, apply?, expectedVersion?}` → `{configVersion, applied, changes}`; an invalid document is `400 invalid_config_document` naming the path; `apply` without `expectedVersion` is `400 expected_version_required`; a stale one is `409 version_conflict`; refusals are `409`. An intake label on a Repository without GitHub Coordinates is `409 no_github_coordinates`. `GET /v1/config/audit` lists applied imports.
- **Apply** is one immediate transaction: the version check, the diff again, the writes (the Factory Level row and its `version` when it changed; new Projects; Project configs; each changed Repository's fields, its profile re-stamped `confirmedBy: user:local` when a profile field changed; intake turned off cancels the open intake items, as `repo intake off`), one bump, one `audit_log` row (`config.imported`, target `config`, before `{configVersion}`, after `{configVersion, changes}`) and one `config.imported` event (`entityKind: factory`) carrying the same changes. The per-level events (`factory.config_updated`, `project.config_updated`, `repository.profile_updated`) are not written for an import. An empty diff applies nothing and writes nothing.
- **YAML stays in the CLI.** The API speaks JSON like every other route; the CLI writes the export with the `yaml` package (2.9.1, already in the lockfile as a test dependency; now a dependency of `@factory/cli`) and parses the file before sending it. `config export` prints to stdout with a header comment naming the version; `config import <file>` prints the diff and the exact `--apply --expect-version <n>` command. *(Flagged for review: the version is printed in a comment, not stored in the document, so a committed export doesn't change when only the version does.)*

## Consequences

- Repository Merge Policy and merge method can now be changed after registration, through an import only (there is still no `repo config set`).
- Tests: unit `config-import` (new, 10); scenario `config-import` (new, 3: export with no token values and an empty round-trip diff; diff-only, a stale version refused after a `project config set`, the apply with one event and one audit row, a created Project, the widening flag; refusals of an unregistered Repository, a widening below the parent, an unknown key and unreadable YAML, changing nothing).
