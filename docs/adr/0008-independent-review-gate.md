# The independent review Gate and the full approval rule (Phase A, issue #8)

Choices made while adding the reviewer Harness Run to Task execution and making approval use the full rule. All are routine and reversible.

- **Where the review sits.** After the developer Harness Run, the factory's own Gates run first (ADR-0007). The review runs only when they pass: every required verification command exited 0 on the current commit, HEAD did not move, verification left the Worktree clean, and no mandatory criterion's verifying commands failed (no review could rescue that). Then one transaction records the Task Result claim, the verification runs and their Evidence, and moves the Attempt and the Task to `in_review` (new Attempt state). So the Evidence the reviewer is sent is stored before it starts.
- **A fresh Session, every time.** The reviewer is always started with `start`, never `resume`, so it never shares the implementer's Session. Its `sessionRef` is recorded on the review. The re-prompt is a new Session too. The Fake Harness now gives every Run its own `sessionRef` (`fake-session_<hex>`), so this can be asserted. The reviewer uses the same configured Harness as the developer: `review.require_distinct_model` is policy (Phase E).
- **Review Packet v1** (`ReviewPacketSchema`, stored as `reviews.packet_json`), rendered by template `review-packet@1` (id and hash on the review). Its keys are exactly: `packetVersion`, `subject` (the Job, Task and Attempt ids, plus `headSha` and `baseSha`), `specification` (the stored Specification proposal), `acceptanceCriteria` (the ones the Task covers, with how each is verified), `diff` (`git diff base..head` with external diff drivers and textconv off, cut at 256 KiB, plus the changed paths and a `truncated` flag) and `evidence` (each verification run with its exit code and the last 4 KiB of its output, and each command-sourced criterion verdict). It never contains the Task Result, the developer's output or anything else the Harness produced.
- **The reviewer's working directory is the Worktree at the reviewed head**, so a real reviewer can read the code (ARCHITECTURE §9: "the same one with writes forbidden"). Before it starts, the factory removes `.factory/` from the Worktree: the Task Result was already stored as an Artifact, and it is the implementer's claim, which the reviewer must not see. Tier 0 can't forbid writes, so the prompt asks for none, and afterwards the factory checks. Modified or untracked files fail the Gates. A commit moves the Task Branch, so the review and the Evidence become stale (below). The environment is the Attempt's guardrail environment.
- **Output** (`ReviewProposalSchema`): `outcome` (`approved` | `changes_requested`), `summary`, `findings` (severity, Fault Origin, location, problem, why, recommendation, blocking) and `criteria` (a verdict `pass` | `fail` | `blocked` | `not_tested` per code). It is parsed, schema-checked, then code-checked (`validateReview`): `review.criteria_known` (only codes in the packet), `review.criteria_unique`, `review.blocking_severity` (critical and high always block; PRODUCT_SPEC §8 says "by default", and policy can't change that before Phase E), and `review.outcome_consistent` (approved ⇔ no blocking Finding). One re-prompt carries the problems, as for proposals (ADR-0006). A second invalid output, or a reviewer Run that did not exit 0, fails the Attempt with the new exit reason `review_failed`, and nothing is stored as a review. A crashed reviewer Run is not re-run yet (spec issue 6 allows one such repeat; it needs recovery, #13).
- **Stored once, never regenerated.** A valid review is recorded in one transaction: the `review` Artifact (the proposal as given), the `reviews` row, its `review_findings` (in order), and one `criterion` Evidence row per covered criterion with `review_id` set (a criterion without a verdict gets `not_tested`). A unique index on `(attempt_id, head_sha, base_sha)` makes a second review of the same commit pair impossible. The same transaction decides approval and ends the Attempt.
- **The command-linked criteria stay** (the question the #7 bridge left open, spec issue 16). A Plan verification command may still name the criteria it verifies. Its verdict is Evidence with source `commands`, beside the review's with source `review`. Both are kept, because the command source is deterministic and the review covers what no command checks.
- **The full approval rule** is the pure `decideApproval` in `@factory/domain`. It reads only recorded rows and compares each against the current `(head_sha, base_sha)`, read from git after the review: every required verification run is current and exited 0; there is a review, it is current, and it approved; and every mandatory covered criterion's verdict, combined over its current Evidence from both sources (`fail` > `blocked` > `pass` > `not_applicable` > `not_tested`; none current is `not_tested`), is `pass` or `not_applicable`. Evidence or a review for another commit pair counts as absent (stale). In Phase A the base doesn't move inside an Attempt (there is no re-fetch until Phase C staleness), so the current base is the Attempt's base.
- **Exit reasons:** `completed` (approved); `changes_requested` (a current review requested changes); `review_failed` (no valid review); otherwise `gates_failed` (stale review or Evidence, a mandatory criterion without passing Evidence, reviewer changes). The stopgap from ADR-0007 holds: the Task is `failed` and the Job fails. Rework by Fault Origin is #9.
- **Time limits:** one reviewer Run gets 10 min by default (`reviewWallClockMs`). The Attempt lease now budgets two reviewer Runs: `attemptLeaseMs` = Harness limit + 4 × verification limit + 2 × review limit + 60 s.
- **Delivery Report v2** (`reportVersion: 2`): each delivered Task carries its approving review (outcome, summary, SHAs, reviewer, Findings), and its criterion verdicts combine both sources. The "not independently reviewed" limitation is gone. Every Finding of an approving review is listed as an open known limitation (it was not fixed).
- **API and CLI:** `GET /v1/jobs/:id/reviews` (each review with its packet and Findings). Evidence gains `source` and `reviewId`. Artifact kind `review`. `factory job show` prints the review and its Findings under the Attempt. Events: `review.recorded`, and `harness_run.*` now carry `role` (and `reprompt` on a re-prompt).
- **IDs:** `rev_` and `fnd_`. **Migration 0005:** `reviews`, `review_findings`, `evidence.review_id`.
- **Unit tests.** The approval rule and the review checks are pure, so they are tested directly through `@factory/domain` (`tests/unit/`), the first tests outside `tests/scenarios`. The root package depends on `@factory/domain` (workspace) for that.
