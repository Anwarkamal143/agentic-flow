# Multi-repo Jobs: creation, the stored Delivery Order and upstream context

**Status:** accepted (Phase D, #105; builds the execution part of ADR-0052). The choices below are routine and reversible.

## Context

ADR-0052 decided that a Job may span Repositories of one Project, that cross-repo dependency edges in the Plan give the Delivery Order (a cycle makes the Plan invalid), and that a dependent Task gets the upstream Task's result summary and diff as read-only context. Much was already per Repository: Plan Tasks name a Repository, Worktrees and Task Branches live in each Repository's Factory Clone, and one Integration Task is made per Repository the Plan has Tasks in (ADR-0034). What was missing: creating such a Job, the Delivery Order itself, and what a dependent Task sees across Repositories.

## Decision

- **Creation.** `POST /v1/jobs` takes `repositoryIds` (one or more, each once, at most 20) beside the existing `repositoryId` (one; kept so existing clients and tests stay valid; both at once is a 400). Every named Repository must belong to one Project, the named one when `--project` is given (`409 repository_not_in_project`). A Job Merge Policy override must be at least as strict as each Repository's. `factory job create` takes `--repo` repeatedly and resolves each name to an id. The `job.created` event payload keeps `repositoryId` (the first by name) and adds `repositoryIds`.
- **Delivery Order is a pure domain function,** `deliveryOrder(tasks, repositories)`. It lists every Repository the Plan has a Task in, upstream first, each with `after`: the Repositories (in Delivery Order) whose Tasks its Tasks depend on directly. Repositories no edge orders are listed by name, then id. A cycle between Repositories is `{ok: false, cycle}` by name. A list with direct upstreams, not only an order, so the Merge Gate (#106) can wait for exactly the PRs a Repository depends on.
- **`plan.delivery_order_cycle`.** `validatePlan` reports a cycle between Repositories that no Task cycle shows (for example api.a → web.b → api.c). A Task cycle is reported once, as `plan.no_cycles`. The planner gets the usual one re-prompt; a Plan Edit's error goes back to the human.
- **Stored with the Plan's Tasks.** `persistPlanTasks` (the planner's Plan and a human's Plan Edit alike) writes `jobs.delivery_order_json` (migration 0032) and a `job.delivery_order_set` event in the same transaction. A Replan's Plan replaces it. The Job API returns `deliveryOrder` (`null` before a Plan); `job show` prints `delivery order: api → web (web after api)` and the dashboard Job page a "Delivery order" field, both only when the order has more than one Repository.
- **Readiness unchanged; the Dependency Base is per Repository.** A dependent Task becomes `ready` once every Task it depends on is approved, in whichever Repository. Only dependencies in its own Repository make its Dependency Base (ADR-0021): an upstream head lives in another Factory Clone, and the agent gets context, never code.
- **Task Packet v4, template `task-packet@9`: `context.upstream`.** One item per Task of another Repository it depends on, in Plan order: the Task (`id`, `key`, `title`), its Repository, the approved Attempt's `baseSha`/`headSha`, its Task Result summary (the upstream developer's claim, `null` without a valid one), and its diff `base..head` read from that Repository's Factory Clone, cut at 128 KiB (`truncated`). Read from stored records and git each Attempt; nothing is regenerated. The template says it is read-only context, never widens the scope, and is not in the Worktree.
- **Task dependencies are written after every new Task row.** A Plan listing a dependent Task before its dependency hit a foreign-key failure (`factory_error`) in `persistPlanTasks`; the dependency rows are now inserted once all new Tasks exist.
- **The Delivery Report reads each Task's git in its own Factory Clone.** Its version and shape are unchanged: it still describes one Repository (the first by name) and its Integration Branch, and for a multi-repo Job a known limitation names the other Repositories' Integration Branches and Factory Clones and says the branches are not atomic. The per-Repository report (status, Partial Completion, out-of-order merge, pending contract step) is #106.

## Consequences

- Seams for later tickets: the Merge Gate's "earlier PR merged" condition reads `deliveryOrder[].after` (#106); a triage-chosen set (#107) writes `job_repositories` the same way creation does; the per-Repository Integration Review with the other diffs as context (#106) can reuse `upstreamContext`'s diff reading.
- The planner prompt is unchanged: it already sees the Job's Repositories; telling it to write the contract into the upstream Task's acceptance criteria (PRODUCT_SPEC story 60) and to mark contract Tasks deferred is not built here.
- Tests: unit `delivery-order` (order, ties, chains, cross-repo cycle without a Task cycle, unknown dependencies), unit `plan-validation` (+3), scenario `multi-repo` (+2).
