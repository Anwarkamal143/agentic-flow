# Replanning and carry-over

**Status:** accepted (#45, Phase B). Routine and reversible choices inside ARCHITECTURE §4.7 and §8.1 and the Phase B decisions Q12, Q14, Q16 and Q29 (PROGRESS.md "Human decisions"). Builds on ADR-0019 (Plan Edit, "request changes", `replanRequestOf`), ADR-0020/0021 (claims, the Dependency Base), ADR-0023 (Questions) and ADR-0026 (Blocker Approvals, `audit_log`). Pure rule in `packages/domain/src/carry-over.ts`; runtime side in `apps/runtime/src/replan.ts`, `plans.ts` (`persistPlanTasks`), `inbox.ts` and `jobs.ts` (`requestReplan`).

## Asking for a Replan during execution

- **Who asks.** The operator (`POST /v1/jobs/:id/replan {expectedVersion, feedback}`, `factory job replan <job> --feedback <text>`), or an Inbox option: `replan` on a `rework_cap_reached` / `question_cap_reached` Blocker Approval, and on a scope change Question ("replan with this request as feedback", §8 step 6). `base_merge_conflict` (#44) gets the same `replan` option once its Blocker exists on the integration branch. Before execution the Replan is still "request changes" at `plan_approval` (ADR-0019); a request outside execution is `409 not_executing`.
- **What is stored.** In one versioned Job transaction: a `replan_request` Artifact (new Artifact kind, no migration) holding `{planArtifactId, feedback, requestedBy, approvalId}`, then — under `maxReplans` — `jobs.replans_used + 1`, `jobs.replan_requested = true` and a `job.replan_requested` event. The feedback from an Inbox option is the item's title and `why` (for a scope change, the developer's request, labelled agent output) plus the operator's comment. The planner reads the request from that Artifact on every Harness Run, so it is never regenerated; `replan_request` Artifacts are not passed to the planner as ordinary inputs.
- **Counted when asked.** The Replan counts against `maxReplans` in the transaction that records the request, not when planning starts. A second request while one waits is `409 replan_already_requested`.
- **The window.** While `replan_requested` is set, `claimNextTask` claims no Task of the Job (checked in the candidate query and again inside the claim transaction), so no new Task and no Rework Attempt is dispatched; Rework, answers and grants may still ready a Task. Attempts in flight (Task `claimed`, `running`, `verifying`, `in_review`) run to their end. An Attempt ending `needs_decision` settles its Task `blocked` as usual (ADR-0023). Cancelling the Job works as before and clears the flag.
- **Planning starts** in the transaction where the last in-flight Attempt settles (`settleExecution` calls `startRequestedReplan` first; it is also called right after the request when nothing is in flight): the newest `execution` Stage Run becomes `superseded` (new transitions `queued|running|blocked → superseded`), `replan_requested` is cleared, and new Stage Runs are added: `planning` (queued), `plan_approval` and `execution` (pending), each `attempt + 1`, with a `job.replanning` event. The new Plan goes through `plan_approval` under the Job's policy (a `skip` policy records it skipped). Every reader of the `execution` Stage Run now takes the newest one.
- **Planner prompt** `proposal-stage@3`: the Replan section now says that a Task kept exactly as it is keeps its work, and the request is labelled as feedback, never permission.

## At the cap

At `maxReplans`, the request (still stored as a `replan_request` Artifact) waits in a Job-level `replan_cap_reached` Blocker Approval instead: `kind: blocker`, `task_id` null, subject = the request Artifact, options `grant_replan` and `cancel_job`. Execution goes on meanwhile; a second request while it is open is `409 replan_cap_pending`. `grant_replan` (no size: exactly one) sets the Job's frozen `maxReplans` to `max(used, cap) + 1` with source `job`, writes one `audit_log` row (`cap.raised`, `target job:<id>`, before/after `{maxReplans}`, `policy_ref inbox:<item>/grant_replan`), then starts the held request as above. `BlockerReason` gains `replan_cap_reached`; it is never stored on a Task, only named by the item's options. The `replan` option of the cap Blockers and the scope Question also land here at the cap (the triggering item is decided `replan`; its Task stays blocked until the cap item is decided).

## Carry-over: one pure decision

`decideCarryOver(current, next)` runs whenever a Plan's Tasks are stored (a planner's Plan, or a Plan Edit), against all of the Job's Tasks:

- **Identity.** A Task carries over only if it is unfinished, its key exists in the new Plan, its whole Plan entry is identical (compared by value with the repository resolved to its id, so key order and name-vs-id don't matter; array order does), and every Task it depends on carries over (so the whole chain is identical). The entry compared is the one in the Plan the Task last came from (its `plan_artifact_id`), not the Task row, whose caps may have been raised by grants.
- **By state.** `pending`/`ready` carry over and are recomputed (`pending → ready` when every dependency carries over `approved`). `changes_requested` and `blocked` carry over as they are; a blocked Task keeps its open Inbox Item. `approved` carries over only if `approvalStillHolds`: its last Attempt `passed` on a recorded head, it has Evidence, and every Evidence row and review of that Attempt ran on exactly its `(head_sha, base_sha)`. A Task in flight makes the decision throw (it is never taken while one is). `cancelled`, `failed` and `integrated` are finished: never carried over, never cancelled again.
- **Carried** Tasks keep their id, so their Task Branch, Worktree, every Attempt and their cap counts; their `plan_artifact_id` moves to the new Plan (event `task.carried_over` with the replaced Plan).
- **Everything else unfinished is cancelled** (reason `replan`, with the miss: `removed`, `definition_changed`, `dependency_not_carried`, `approval_stale`, `resolved_by_replan`), its open Inbox Items `cancelled` (`task_cancelled`), its Worktree left `preserved`. An approved Task whose definition changed is cancelled (new transition `approved → cancelled`); its passed Attempt and head stay on record, and the new entry runs as a new Task.
- **New Tasks.** Every entry nothing carries becomes a new Task: new id, fresh cap counts, fresh Worktree and Task Branch (`task.created` names the Task it `replaces`, if any). That includes an identical definition of a cancelled or failed Task: its fresh counts are bounded by `maxReplans`, since each such restart costs a Replan. Worktree paths are now `<job>/<task-id>-<key>` (were `<job>/<key>`), so a re-planned key never collides with the preserved Worktree of the Task it replaces; the old branch is kept, never reused.
- **A Task whose Item triggered the Replan is affected.** A blocked Task whose Blocker Approval or Question was decided `replan` is never carried over (`resolved_by_replan`): the human asked to replan because of it. Carrying it over would leave it blocked with no open item. This reads Q29's "blocked keeps its Inbox Item unless this Replan resolved it" strictly (Spec issue 28).
- **Before execution too.** "Request changes" and a Plan Edit no longer cancel the replaced Plan's Tasks up front; the carry-over decides when the new Plan is stored. An identical Task of a never-run Plan therefore keeps its id. A rejected Plan still cancels its unfinished Tasks (now including any carried-over `blocked` ones, with their items); a failed planning Stage cancels the Job's unfinished Tasks and their items.
- **No Task to claim.** If the approved new Plan has no `ready` Task (everything carried over `approved` or `blocked`), queueing `execution` runs and settles it at once, so the Job completes or waits on its Blockers instead of hanging.
