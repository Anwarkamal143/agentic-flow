# The clarification engine for proposal Stages

**Status:** accepted (Phase D, #111; builds PRODUCT_SPEC §5's clarification engine as decided in Phase D grilling Q14). The choices below are routine and reversible; three (the Stage-level Blockers with no Inbox item, a re-specification never asking, and reusing `maxQuestions`) are flagged for human review.

## Context

Q14 decided: triage and specification output categorized `questions[]`, routed in code. Discoverable: the Stage re-runs once with a discovery instruction; still open, it blocks with no Question. Technical: the agent decides, kept as an ADR-style Artifact. Product, Security, Operational: one Inbox Question batch per Stage Run, grouped by category, each with options and a recommended default (Security marked as needing approver rights). Answers start a new Stage Run with the answers as input; the earlier output stays an Artifact and is never regenerated. `maxQuestions` caps it per Stage; over the cap blocks. The execution question protocol (ADR-0023) is the prior art.

## Decision

- **Schema.** `TriageProposal` and `SpecificationProposal` gain optional `questions` (at most 20), each `{category, text, options, recommended?, decision?, rationale?}` (`ClarificationQuestionSchema`). The validators add `clarificationIssues`: a Technical question needs the agent's `decision` (`clarification.technical_decision`); a Product, Security or Operational one needs at least two `options` (`clarification.options`) and a `recommended` one of them (`clarification.recommended`). A broken shape gets the usual one re-prompt. Discovery and planning ask nothing.
- **Routing** is the pure `routeClarification({questions, discoveryRerunUsed, batchesUsed, maxQuestions})`, in this order: any Discoverable question → `discover` if the Stage has not yet had its discovery re-run in this Job, else `blocked` (`discoverable_unresolved`); then any human question → `ask` while fewer than `maxQuestions` batches were asked for the Stage in this Job, else `blocked` (`clarification_cap_reached`); else `proceed`. Technical questions never stop a Stage. The counts come from the Stage's `clarification` Artifacts (below), so they are per Stage, per Job.
- **Artifacts.** Two new kinds. `decision_record`: one per Stage Run that made Technical decisions, `{stageId, stageRunId, decisions: [{question, options, decision, rationale, agentProposed: true}]}`, written whatever the route; it names its Stage Run in its content, not `stage_run_id` (which holds one proposal Artifact per Stage Run). Later Stages read it as an input. `clarification`: the output of a Stage Run that stopped on its questions, `{stageId, stageRunId, route, output, questions}`; it is never applied (no Acceptance Criteria, no Repository set) and never regenerated, and only the same Stage's later runs read it.
- **Discover.** The Stage Run is `superseded` (`discovery_rerun`) and a new one of the same Stage queued (`attempt + 1`). Its prompt carries the earlier round and the instruction to find the Discoverable questions in the Repository itself.
- **Ask.** The Stage Run waits `waiting_human` (reason `awaiting_answers`) on one `question` Inbox Item: no Task, the Stage Run held, the subject and evidence the `clarification` Artifact, the only option `answer`. Its questions are `source: clarification`, all blocking and agent-proposed, numbered `q1…` in category order (product, security, operational), each with its `category`; a Security question has `requiresApprover: true`. For a single-user factory this is a mark only (`inbox show` prints "security (needs approver rights):", the dashboard a badge); no RBAC is built. Answering (`answerQuestion`, the same API and CLI as ADR-0023) supersedes the Stage Run (`answered`) and queues a new one in the same transaction. Its prompt lists every earlier round of the Stage with the human's answers, as guidance that never changes a permission; `harness_run.started` records `clarification.rounds` (each round's Artifact, route, and the answers or the questions to discover).
- **Blocked.** *(flagged for review)* The Stage Run goes `blocked` with a `policy` Blocker and opens no Inbox item, so the Job is `blocked`, `job show` names the reason, and the way on is cancelling the Job (a Blocker Approval with "grant one more batch" could come later). A proposal Stage has no Task or Attempt: its Blocker's `taskId` holds the Stage Run's id and `attemptId` the `clarification` Artifact's.
- **The prompt** is `proposal-stage@9`: triage and specification are told the categories and how to ask (its hash covers the new text), and a re-run gets a "This Stage ran before" section with its rounds.
- **A re-specification never asks.** *(flagged for review)* A `specification` Stage Run after a Finding (ADR-0031) answers that Finding; its output may record Technical decisions, and any other question is refused (`clarification.respecification`, the one re-prompt). `respecRequestOf` tells a clarification re-run (its previous Stage Run holds a `clarification` Artifact) from a re-specification, which until now was any `specification` Stage Run after the first.
- **The cap** *(flagged for review)* is the Job's `maxQuestions` (Effective Configuration, default 3), the same key that caps a Task's answer Attempts, counted separately per Stage.
- **Recovery.** Every route is written in the transaction that ends the Stage Run's Harness Run, so a restart finds a superseded, waiting or blocked Stage Run and runs nothing again; only a queued re-run starts a Harness Run, and it reads the stored rounds.

## Consequences

- An unclear Job reaches the human early, before any Plan, with grouped options and defaults; and Discoverable questions never reach the human.
- An answered round costs one more Harness Run of the Stage. The output that asked is kept for audit but is not what the Job runs under.
- Tests: unit `clarification` (new, 13: the routing per category, grouping and the Security mark, the cap, the shape rules, the schemas, the Decision Records); scenario `clarification` (new, 5: a grouped batch answered from the CLI and the Job completing with the earlier output kept; a missing recommended default re-prompted; past the cap blocked with only one item ever opened; a Discoverable question re-run once and never asked; still open after the re-run, blocked with no item, then cancelled). `contract-follow-up` and `verification-commands` expect `proposal-stage@9`.
