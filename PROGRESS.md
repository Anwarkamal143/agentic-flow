## Known limitations

- Dashboard (#15, ADR-0014; #37, ADR-0022): the job list, the job detail with its read-only plan view, live activity, the Inbox and an Artifact page exist (the board, projects and system health are not built). The Inbox is the only write path (decide, defer, undefer); the job detail doesn't show worktrees or logs (`factory logs`), the plan view has no Task priority (the plan API doesn't return it) and no drawn DAG, and the Inbox has no "cancel the Job" action (replan-with-feedback, #38: see below). An Inbox Item of a kind other than `plan` shows "None recorded" for its risks (an `Approval` has no risk field). No dashboard login: it trusts loopback, as the runtime's files do; writes also require the dashboard's own `Origin`. The client-side live code (EventSource, `router.refresh()`) has not been exercised in a real browser by a test; the scenarios cover the server rendering, the form posts and the SSE pass-through. There is no loading skeleton, because a streamed response would send 200 before a missing Job's 404. Each refresh re-reads the Job's whole event log (Harness progress events are counted, not stored, so the log holds state changes only).

- Replan-with-feedback (#38) has no dashboard action or dashboard scenario on the #38 branch. The dashboard had no write path there, and #38 did not own `apps/dashboard/**`. The API (`POST /v1/jobs/:id/plan/request-changes`), the CLI and the plan item's `request_changes` option are built. #37's Inbox renders options generically, with a comment box, so once both are merged the option should show there, with the comment as the feedback. A dashboard scenario for it (and a check that an empty comment shows the `feedback_required` refusal) is still to be written.
- `factory stop` won't signal a runtime that doesn't answer its API. The operator must kill that pid by hand.
- `factory doctor` checks Claude Code's stored login by `claude auth status`'s exit code (#14). `gh auth status` needs the network, so offline it reports the gh login absent. No minimum tool versions are enforced yet.
- `factory repo add` takes a path only. Registering by URL (PRODUCT_SPEC §13 `<path|url>`) isn't built. Command detection covers `package.json` projects only. There is no `repo list` CLI command yet (the API has `GET /v1/repositories`).
- Proposal Stages and Tasks run only when a Harness is configured (`config.json` `harness`, `fake` or `claude-code`, which has to be edited by hand; there is no CLI command for it). Without one, a new Job waits at `triage: queued`, and recovery doesn't run.
- Task execution (#7, ADR-0007) has stopgaps: a Task Result still invalid after its one re-prompt (#10, ADR-0010), a non-`done` status or a Harness failure fails the Task and the Job (no Retry #13, no questions until Phase B). The Delivery Report doesn't mention a re-prompt; only the events do. Failed Gates and reviews go to Rework (#9). The base comes from `git fetch origin` in the Factory Clone, so a clone whose origin is a network URL needs the network.
- The review (#8, ADR-0008) has stopgaps: an invalid review fails the Task and the Job. A reviewer Run that crashes while the runtime is alive is `review_failed`; only after a runtime crash is the review run again (ADR-0012).
- Cancellation and recovery (#12, #13, ADR-0012): only a runtime crash gives a Retry; a Harness Run that times out or crashes under a live runtime still fails the Task (no backoff). A graceful `factory stop` cancels the process in flight, so its Attempt is recovered as interrupted (a Retry), not re-attached. Between a crash and the next start a spool holds raw, unredacted output in the factory home. A process that leaves its group (`setsid`) is not stopped. A crash between `addWorktree` and its row leaves a directory the next claim fails on (`factory_error`). Proposal Runs are not re-attached (the Stage starts again). Nothing clears a recovery Blocker yet (Phase B). Cleanup prompts on cancel are Phase B.
- Rework (#9, ADR-0009): nothing clears a Blocker yet. A `waiting_human` or `blocked` Job can only be cancelled (the Inbox, replanning and re-specification are Phase B). A Gate Finding always has Fault Origin `implementation`, even when the reviewer dirtied the Worktree (`worktree.clean`). Such reviewer leftovers would then be committed as the next Attempt's WIP commit, flagged. Only the previous Attempt's Findings are carried into the packet. The reviewer is the same Harness as the developer (`review.require_distinct_model` is Phase E). Tier 0 can't stop the reviewer writing; the factory only detects it afterwards (a changed Worktree fails the Gates, a commit makes the review stale). The base is never re-fetched inside an Attempt, so base staleness isn't exercised before Phase C. Findings of an approving review are listed in the Delivery Report as open, and nothing acts on them.
- `apps/runtime/src/execution.ts` is still ~2,040 lines after #34 moved the review flow and its transaction into `review.ts` and closure into `closure.ts`: the class keeps the claim, the developer and reviewer Harness Run plumbing (start, re-attach, finish), verification and its record-keeping, the Attempt's end (`endAttempt`, Rework routing), cancellation and `factory_error`. The next candidate split is verification (`verifyStep`, `verify`, `recordVerification`, `inspect`) into its own module.
- Proposal Harness Runs are recorded as events only (ADR-0006). Their progress events are counted, not stored. A crash between a first invalid output and its re-prompt gives the Stage a fresh pair of Runs. Triage can't reject a Job yet. The Plan validator checks overlapping writable paths of parallel Tasks (#36, ADR-0017) by static prefix, which is conservative (`src/*.ts` and `src/*.css` count as overlapping). Task priority is not shown by the Task API, `job show` or the dashboard yet. Dispatch order has no aging or project share (v1); time ready comes from the event log, as there is no `ready_at` column.
- The Effective Configuration has one setting (`maxAttempts`) and two levels (recipe, Project). The Project config can be set only through the API (`POST /v1/projects/:id/config`); there is no CLI command and no re-freeze of a Job's config.
- `job show` doesn't list events (use `GET /v1/jobs/:id/events`). `factory logs` shows Attempt output only; proposal-Stage output is in its Artifacts.
- Redaction (#11, ADR-0011): secrets are marked by variable name only (no config to mark one yet); the pattern set is a Phase A subset (the corpus is E3). A secret the Harness writes into a file stays in the Worktree, the Factory Clone and git history (the Repository's content; no secret-scan Gate yet). Output past the 1 MiB limit is cut at its start, so a secret straddling the cut can leave an unmatched fragment. Harness progress events are counted, not stored.
- Claude Code adapter (#14, ADR-0013): API-key billing is built (ADR-0015). Under it the key is readable by the Harness and every command it runs (Tier 0). Its cost is an estimate (list price or a configured table; cache writes at one rate), and no real run billed to a key has been made. No `CLAUDE_CODE_OAUTH_TOKEN` grant. The usage window (`paused_until`) is Phase E (E2): a Harness Run that hits a usage limit fails with the CLI's reason. `--max-turns` is not listed in `--help` and so not verified offline. The subscription login is found through `HOME` and `USER`; a runtime started without `USER` gets `Not logged in`. The developer's own `git commit` runs Repository hooks. Claude Code keeps Session transcripts under the operator's `~/.claude/`, unredacted by the factory. Proposal output must be bare JSON; a fenced reply is rejected and re-prompted like any invalid output. The factory installs no dependencies in a Worktree (Tier 0 refuses repo setup scripts), so a real developer installs them itself (`npm install`, network not enforced) or its typecheck fails; when the runtime is started through `pnpm`, PATH also carries the factory's own `node_modules/.bin`, so a Worktree finds this repo's `tsc`/`vitest` (seen in A7).
- The localhost-only scenario checks a non-loopback IPv4 only when the machine has one.
- Parallel DAG (#39, ADR-0020/0021): a Dependency Base merge conflict fails the Task with `factory_error` until #44's `base_merge_conflict` Blocker; a failed Task's dependents stay `pending` until #44's `dependency_failed`. Closure's `git worktree remove` is not under the per-clone setup lock, so a closure and another Job's Worktree setup on the same clone may still race on git's lock files (seen nowhere yet). Per-project and per-harness capacity are not built (v1, Phase E).

- Decided out of Phase B (grilling 2026-11-09): `scope_change_request` grants (spec issue 23, Phase E; shown as an Inbox Question), repo `services` locks (spec issue 24; two Tasks on one repo may share a test database unless the repo uses `FACTORY_TASK_ID`), proposal-Stage clarification questions (spec issue 25, Phase D), base staleness of carried-over Tasks after a Replan (mixed bases; Phase C), and the 24 h Approval reminder (notifications are v1; Approvals `remain_pending`).

- Questions (#42, ADR-0023): a scope change request's Question offers only the answer; "replan with this request as feedback" arrives with the Requested Replan ticket (#45). `question_cap_reached` has no Inbox Approval until #43 (cancel the Job is the only way on). A Replan or the `plan` route doesn't yet cancel a cancelled Task's open Question (#45/#46); a Job cancel does. Every answer Attempt is a new Harness Session (`resume` unused).
