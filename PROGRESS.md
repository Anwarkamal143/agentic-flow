- 2026-11-08 — Fix: the schedulers busy-looped when idle (since #6). Both the Stage and the Task scheduler started another pass right after every pass, also an empty one, so an idle runtime with a Harness configured spun on SQLite queries at a full core (measured 3.1 CPU-seconds per 3 s idle; ~0 after). With one runtime per scenario, the full suite could saturate the machine and Jobs missed their deadlines. Both schedulers now share one loop (`apps/runtime/src/pass-loop.ts`): a pass reports whether it did work, and only then, or when a wake arrived during the pass, does the next pass start at once; otherwise the 1 s poll timer drives it. Regression scenario `tests/scenarios/scheduler-idle.test.ts` (CPU time of an idle runtime, from `ps`). Branch `phase-a/fix-scheduler-busy-loop`.

## Known limitations

- `pnpm dev` isn't defined yet (no dashboard). The runtime runs through `factory start` or `node apps/runtime/dist/main.js`.
- `factory stop` won't signal a runtime that doesn't answer its API. The operator must kill that pid by hand.
- `factory doctor` doesn't detect Claude Code's own stored login (`claude /login`: Keychain / `~/.claude`). Only env tokens are checked for Claude. `gh auth status` needs the network, so offline it reports the gh login absent. No minimum tool versions are enforced yet.
- `factory repo add` takes a path only. Registering by URL (PRODUCT_SPEC §13 `<path|url>`) isn't built. Command detection covers `package.json` projects only. There is no `repo list` CLI command yet (the API has `GET /v1/repositories`).
- Proposal Stages and Tasks run only when a Harness is configured (`config.json` `harness`, which has to be edited by hand; only `fake` exists until the Claude Code adapter lands). Without one, a new Job waits at `triage: queued`. `factory job cancel` refuses a Job whose Stage is `running` (process termination is #12).
- Task execution (#7, ADR-0007) has stopgaps: any failed Gate, invalid or missing Task Result, non-`done` status or Harness failure fails the Task and the Job (no Rework #9, no re-prompt #10, no questions until Phase B). There is no review (#8) and no path-scope Gate (#9); the Delivery Report says so. Output isn't redacted yet (#11). Shutdown during an Attempt leaves it `running`, with no recovery yet (#13), and the lease has no heartbeat. Only one Attempt per Task (`n = 1`). The base comes from `git fetch origin` in the Factory Clone, so a clone whose origin is a network URL needs the network. A closure cut short by a crash stays `running` until #13 (it resumes from the existing report and never writes a second one).
- `apps/runtime/src/execution.ts` (~1,250 lines) holds the claim, the Worktree and port code, the Harness Run, verification, the record-keeping, closure and the Attempt/Worktree transition helpers. Follow-up before #8, as its own change: move the Worktree and port code to `workspace.ts` (ARCHITECTURE §2 sketches `scheduler/` and `workspace/` separately), and move `stepAttempt`/`stepWorktree` into `engine.ts` next to `stepTask`.
- Proposal Harness Runs are recorded as events only (ADR-0006). Their progress events are counted, not stored. A crash between a first invalid output and its re-prompt gives the Stage a fresh pair of Runs. Triage can't reject a Job yet. The Plan validator doesn't check overlapping writable paths of parallel Tasks (Phase B).
- The Effective Configuration has one setting (`maxAttempts`) and two levels (recipe, Project). The Project config can be set only through the API (`POST /v1/projects/:id/config`); there is no CLI command and no re-freeze of a Job's config.
- `factory logs` isn't built yet; `job show` doesn't list events (use `GET /v1/jobs/:id/events`).
- The localhost-only scenario checks a non-loopback IPv4 only when the machine has one.

Logged 2026-11-08, Round 2:

6. **Attempt cause and retry limit.** `attempts` has no field saying why the Attempt exists. Proposed: `attempts.cause: initial | rework | retry`, or derive it from the previous Attempt's `exit_reason`. There is also no separate `max_retries`: give it a config default, separate from `max_attempts`, which caps Rework only. Inside one Attempt only two repeats are allowed: the single `invalid_output` re-prompt, and re-running a crashed review Harness Run (head_sha unchanged). A usage-window pause is capacity, never a Retry or Rework. Write an ADR if the limits turn out non-obvious.
7. **The `never_auto` and `human_approval` merge policies aren't distinguished** (PRODUCT_SPEC §9). Proposed reading: under `never_auto` the factory never merges; it waits for a human to merge on GitHub, which polling detects. Under `human_approval` the factory merges after an Inbox Approval. While it waits on the external merge, the Job is `waiting_human` with a human-kind Blocker. A PR closed without merging opens an Inbox Question and never auto-cancels the Job. Phase C scope.
8. **No human-initiated replan during execution.** Today replanning happens only through the `fault_origin: plan` route or the pre-approval "replan" action. Proposed: a `requestReplan` API operation in Phase B. Each replan writes a new plan Artifact; Tasks in `approved`/`integrated` and unaffected pending Tasks carry over; the count is capped by `max_replans`. Not in Phase A.
9. **Job status precedence (clarifies ARCHITECTURE §4.2).** `active` if any Stage Run or Task is running or queued; otherwise `blocked` if any non-human Blocker exists; otherwise `waiting_human` if any human Blocker exists. Hitting a rework or replan cap creates a human-kind Blocker, so the Job shows `waiting_human` and never loops. Blocker kinds: human, infrastructure, recovery, policy. An unmet dependency is the Task state `pending`, not a Blocker.
12. **ARCHITECTURE §10 `--reference` "to save disk".** A plain `--reference` makes the Factory Clone depend on the user's object store (alternates), so a `git gc` there can corrupt the clone. #4 uses `--reference --dissociate` instead (ADR-0004): it saves network transfer and time, but not disk. Proposed fix: reword §10 to "`--reference <path> --dissociate` to save network and time". Also, §5 `repositories` gains `created_at`.
13. **ARCHITECTURE §5 `stage_runs` has no ordering column**, so a Job's position can't be read back in Recipe order. #5 adds `stage_runs.position` (ADR-0005). Proposed fix: add `position` to §5. (#6 adds `stage_runs.failure_json`, the failure reason; a rejection could use it.) Also, §4.2's status table has no Stage Run state that yields `rejected`; still open, since #6 doesn't build triage rejection. Proposed fix: say a triage rejection ends the triage Stage Run as `failed` with a `rejection` outcome, or add a `rejected` Stage Run state (to decide in #6).
